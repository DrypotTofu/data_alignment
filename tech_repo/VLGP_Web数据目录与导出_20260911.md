> 范围：`src/vlgp/web/`（§1 视频导出、§2 数据目录、§3 缓存维护）+ 测试夹具/探针。

## 1. IN/OUT 视频导出（pipeline kind=video）

### 1.1 三个分支（`POST /api/sessions/{name}/pipeline/video`）

| 会话状态 | 请求 | 行为 | 任务标签 |
|---|---|---|---|
| 有 `annotations.json.trim` | 任意 | 每台相机加 `--start-sec/--end-sec` | 导出裁剪区间视频 |
| 无 trim | 无 `confirm` | **HTTP 409 + `{warning:true,message}`**，不启动任何任务 | — |
| 无 trim | `?confirm=1` | 导出全部预览视频 | 导出预览视频(全部) |

前端（`startPipeline`）遇 409 弹 `window.confirm`，确认后重新 POST `?confirm=1`。

### 1.2 每相机的精确时间映射（`video_trim_args`）

IN/OUT 是**对齐表行号**（30 Hz 网格，闭区间），预览视频按**各相机自己的 metadata 时间轴**裁切，因此：

```
row -> 对齐表该相机的 filename 列 -> 该相机 metadata.csv 的 timestamp_ns
    -> (ns - 该相机首帧 ns) / 1e9 = 相对秒
```

`_TRIM_COLS = {camera_arm_2: anchor_filename, camera_arm_1: camera_arm_1_filename, camera_arm_3: camera_arm_3_filename}`
（列由 `align_camera_anchor` 写入，仅当该相机存在时才有）。

**回退**：库里没有该列（旧的/单相机会话）→ 用网格相对秒 `row/30`，返回值 `source='grid'`；日志头部逐相机打印 `行 [s,e] -> a~b s (exact|grid)`，便于核对。

> 注意：三台相机"相对各自首帧的秒数"在三台**同时启动**时是恒等的（首帧偏移被抵消）。因此"是否真的用了逐相机映射"只有在相机起始时刻不同时才能验证——这正是 §4 合成夹具的设计动机。

### 1.3 修掉的两个真实缺陷（实测发现）

1. **OUT 帧被丢弃**：`images_to_video` 用 `lo <= timestamp_ns <= hi` 判定，而 `hi` 由 `float` 秒反算成 `int` ns。原先 `round(sec, 6)` 会把 `hi` 算少 1 ns → 行 `[10,30]` 实测只导出 **20 帧（idx 10..29）**，OUT 行丢失。
   **修复**：窗口两侧各外扩 `_TRIM_EPS_SEC = 1e-6 s`（1 µs ≪ 33 ms 帧间隔），并把参数格式化为 `%.9f`；实测 `[10,30] -> 21 帧 (idx 10..30)`，与 `build_srth_dataset` 的闭区间口径（`start_row <= row <= end_row`）一致。
2. **缺 metadata.csv 的相机让整条序列中断**：`start_sequence` 遇到第一台无法导出的相机即 `exit 1`，后面相机不再执行。现在请求时先检查 `metadata.csv`，**跳过**缺失相机并在日志写"跳过无 metadata.csv 的相机: …"；全部缺失才返回 422。

### 1.4 管线日志目录

任务日志从仓库 `var/web_pipeline/` 改为跟随当前数据目录 `<数据根>/_web_logs/`（`_resolve_log_root`；目录不可写时回退仓库 `var/web_pipeline`）。

## 2. 数据目录选择（用户决策：C + A + B）

- **C**：内置目录浏览器 + 手动输入路径 + 一键"打开资源管理器"；
- **A**：预览缓存与管线日志**跟随所选目录**（`<根>/_web_preview`、`<根>/_web_logs`），不占用仓库所在磁盘；根目录只读时缓存回退仓库 `var/web_preview`；
- **B**：同时可查看/修改**采集输出目录**（`base_dir`），为后续把采集操作并入 Web 做准备。

### 2.1 端点

| 端点 | 说明 |
|---|---|
| `GET /api/settings` | 当前根、可写性、缓存/日志目录、磁盘余量、会话数、最近目录、采集配置信息 |
| `PUT /api/settings/root` | `{path, sync_acquisition}`；切换并**持久化**到 `var/web_settings.json`（最近 8 个） |
| `GET /api/fs/drives` | 各卷 + 容量（`shutil.disk_usage`） |
| `GET /api/fs/list?path=&files=` | 子目录（标记 `is_session` / `n_sessions`），**只列目录名，不含文件内容** |
| `POST /api/fs/reveal` | 用系统资源管理器打开（仅本机/私网客户端） |
| `PUT /api/settings/acquisition` | 写回采集 `base_dir`（注释保留的行级改写） |
| `GET /api/settings/cache`、`POST /api/settings/cache/clean` | 缓存用量扫描 / 删除失效缓存（见 §3） |

`GET /api/sessions` 现在同时返回 `root`。

### 2.2 切换守卫（重要）

预加载与管线任务在**启动时**就把路径解析到旧根，因此只要有任何后台任务在跑（`PreloadRegistry.running()` / `PipelineJobs.running_jobs()`），`PUT /api/settings/root` 返回 **409** 并列出阻塞任务（预加载：<会话名> / <任务名> (<job_id>)）。

切换成功后：`SessionIndex.set_root()` 清空对齐表缓存 → `reset_frame_cache()` 清 RAM JPEG LRU（**LRU 键含缓存目录**，否则同名会话会串到旧根的帧）→ `PreloadRegistry.reset()`（任务按会话名登记，跨根会撞名）。

### 2.3 子目录约定

数据根下 `_`/`.` 开头的目录不进入会话列表，用于 `<根>/_web_preview`、`<根>/_web_logs`。

### 2.4 采集输出目录（`base_dir`）

`scripts/config/default.yaml`（`start_manual_acquisition.bat` 使用）与 `scripts/config/example_acquisition.yaml`（`run_acquisition.py` 默认 `--config`）两份**同时**改写，保持不漂移；相对路径按仓库根解析后写**绝对路径**（采集进程按 CWD 解析，绝对路径两种启动方式都正确）。改写用行级替换而非 `yaml.safe_dump`，以保留两份配置里的相机/格式注释。

## 3. 缓存维护（存储空间）

用户磁盘现状：旧缓存目录 `var/web_preview` 里 **6.79 GB / 367k 文件属于 11 个已删除会话**（现存 3 个会话只占 ~20 MB）。因此新增"扫描 + 删除失效缓存"：

- `scan_cache()`：按会话统计占用，`stale = 会话已不在当前根`；扫描范围 = 当前根缓存 + 仓库旧缓存目录；UI 显示"共 X MB / 其中失效 Y MB (N 个)"，删除需二次确认。
- `clean_cache(confirm=True)`：只删**已知缓存根的直接子目录**中会话已不存在的那些（防越界）；返回删除数量与释放空间。
- **性能修复**：原先用 `os.walk + os.path.getsize` 统计 → **106.6 s**（请求超时，前端看起来像卡死）；改用 `os.scandir` + `DirEntry.stat()`（Windows 下目录枚举已带大小，无额外 syscall）→ **0.81 s（131x）**。见 `probe_cache_scan_speed.py`。
- 已把现存 3 个会话的缓存从 `var/web_preview` 迁移到 `sessions/_web_preview`（同盘移动，瞬时）。

## 5. 顺带修复的两个健壮性问题

1. **整段预加载对单相机会话必崩**：`PreloadRegistry._run` 用 `df[FILENAME_COLS[cam]]` 取三路文件名，单相机/旧会话缺列 → 线程 `KeyError` 直接死掉（`finally` 把 `current` 填成 `total`，所以前端看起来"完成"，实际一帧没编码）。现在只预加载**对齐表里真有 filename 列**的相机，并给任务加 `error` 字段（异常不再只打印到 stderr）。
2. **缺相机列返回 500**：`SessionIndex.frame_filename` 用 `df.iloc[row][col]`，列不存在时抛 `KeyError` → HTTP 500。现在显式抛 `FileNotFoundError`（→ 404），`/frames/batch` 也不再因单相机会话 500。
3. 缓存读取校验 + 原子写入：磁盘缓存现在校验 JPEG 首尾魔数（`FFD8`/`FFD9`），损坏则重新编码；写入改为临时文件 + `os.replace`，避免异常中断留下半张图被永久当缓存。

## 6. 真实三机位数据实测（E:\sessions 备份）

用户提供 `E:\sessions`（336 GB，9 个会话，**全部三机位齐全**，8 个已对齐，1 个待对齐），据此做了只读实测（`scripts/test/probes/inspect_data_root.py`，不写入该目录）：

| 会话 | 行数 | 相机 | 逐相机导出起点 vs 网格口径 |
|---|---|---|---|
| test_20260828_154441 | 9626 | 3/3 | arm2 −0.5 ms / arm1 **−999 ms** / arm3 **−1079 ms** |
| test_20260828_155305 | 10579 | 3/3 | arm2 +5.6 ms / arm1 −950 ms / arm3 −1060 ms |
| test_20260828_160450 | 776 | 3/3 | arm2 +0.7 ms / arm1 −1060 ms / arm3 −1076 ms |
| test_20260828_160525 | 1117 | 3/3 | arm2 +0.5 ms / arm1 −917 ms / arm3 −1029 ms |
| test_20260828_160624 | 13343 | 3/3 | arm2 +3.4 ms / arm1 −1005 ms / arm3 −1116 ms |
| test_20260901_113003 | 56268 | 3/3 | arm2 +138 ms / arm1 −870 ms / arm3 −902 ms |
| test_20260901_144929 | 94263 | 3/3 | arm2 +1136 ms / arm1 +172 ms / arm3 +108 ms |
| test_20260901_155248 | 99 | 3/3 | arm2 +6 ms / arm1/arm3 −800 ms |

结论：
- 8 个已对齐会话**都有三路 filename 列**，`video_trim_args` 全部走 `exact`；
- **腕部相机比锚点晚启动约 0.8–1.1 s**（≈24–33 帧），所以"网格相对秒"回退会**整整裁错近 1 秒**——逐相机映射不是锦上添花，是必需项；
- 少数会话的锚点本身也有 +0.1~+1.1 s 偏差（漂移/起始差异），说明网格口径在长会话上完全不可用。

### 6.1 顺带提速：会话列表不再 parse 对齐表

旧实现 `session_info()` 用 `len(self.alignment(name))` 取行数 → **列一个根就会用 pandas 解析每个对齐 CSV**（190 列 × 94k 行 ≈ 0.3 s/会话，并把 ~140 MB DataFrame 常驻 `_align_cache`）。E: 上 9 个会话实测 **2.4 s + 数百 MB 内存**。

改为 `row_count()`：按 1 MB 分块数换行符（并处理末行无换行），**2.4 s → 0.17 s（19 ms/会话）**，不再缓存 DataFrame；8 个会话逐一与 pandas `len(df)` 对比**全部一致**。真正需要数据时（帧/曲线/裁剪/校验）仍走 `alignment()`。

### 6.2 失效缓存实际清理结果

按用户决定执行（走 Web 的真实接口 `/api/settings/cache/clean`，`probe_cache_clean.py`）：

```
扫描 4.0 s：14 个缓存目录 / 7320 MB，其中失效 11 个 / 6956 MB
删除：11 个目录、释放 6956 MB、耗时 286 s（367k 个小文件）
结果：缓存 364 MB / 3 个目录（均为现存会话），失效 0，旧 var/web_preview 已空
```
其中 `test_20260901_144929` 一个就占 5123 MB / 283k 文件。**注意**：删除几十万小文件需要数分钟，界面在确认框与状态文本中都已提示"可能需要数分钟，请勿重复点击"。
