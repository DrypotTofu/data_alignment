## 1. 采集端改造（保持 CLI 兼容）

### 1.1 优雅停止通道 `vlgp/acquisition/stop_signal.py`

录制必须优雅停止（写入器刷盘 + 写 `session.json`），所以控制器不能直接 kill。`StopSignal` 提供两个**互相独立**的触发源，都汇总到一个 `threading.Event`：

| 触发 | 参数 | 用途 |
|---|---|---|
| 标志文件出现 | `--stop-file PATH` | 主控制通道（Web 的「停止录制」写文件） |
| stdin 关闭/收到输入 | `--stop-on-stdin-eof`（**显式开关**） | 兜底：控制器（Web 服务）被强杀时管道断开 → 自动优雅停止 |

**`--stop-file` 不再默认监听 stdin**：早期一版默认开启，结果 `start /b`、`Start-Process`、任何把 stdin 重定向为 NUL 的调用方都会**立即触发 EOF**，录制刚起步就停（实测 elapsed=1.1 s）。现在由调用方显式声明"我拿着一个打开的 stdin 管道"，Web 服务正是这种情况。

### 1.2 `manual_acquisition.py`

- 传 `--stop-file` 时**自动开始**（管道 stdin 永远等不到回车），并打印可解析标记：

```
=== ACQ SESSION <name> DIR <dir>          # 进程启动即有（目录已创建）
=== ACQ RECORDING STARTED name=... dir=... t=...
  [recording] camera_arm_2=1234 camera_arm_1=...   # 每 2 s 一行
=== ACQ RECORDING STOPPED reason=<...> elapsed=<s>s
=== ACQ DONE dir=<dir> samples=<name=count ...>
```
- 交互模式（不传 `--stop-file`）完全保留；若 stdin 不是终端会**告警**说明回车送不进来、请用 `--stop-file`。
- `session.stop(timeout=30)` 后再退出，保证 `session.json` 落盘。

## 2. Web 后端

### 2.1 `camera_service.py`

- `scan_cameras(max_index=8)`：逐个 index `open → 读分辨率/FPS → 抓一帧 → release`，得到"哪些 index 真的有相机"。
- `preview_jpeg(index)`：开一次设备抓一帧转 JPEG 后**立即释放**——不长期占用设备，这是预览和采集能共存的前提（录制期间仍直接禁止预览）。
- `config_cameras(path)`：读 `camera_bindings` + 每个相机源的 arm/index/分辨率/是否启用/校验错误。
- `set_bindings(path, bindings)`：**先在校验副本上试写 + `load_config` 校验**（重复 index、arm 无对应源都会抛错），通过后才写真实文件；行级改写，保留注释；并返回 `warnings`——`validate_session_config` 只检查**启用**的相机源，所以"和某个已禁用相机同 index"是潜在冲突，属于警告而非错误。
- `preflight(path, reserve_minutes=20)`：四项检查（见 §3）。

### 2.2 `acquisition_service.py`

- `AcquisitionRegistry`：**同一时刻只允许一个录制**（一套相机）；`start()` 用
  `sys.executable -u -m vlgp.capture.manual_acquisition --config … --name … --stop-file … [--stop-on-stdin-eof]`
  启动子进程，stdout/stderr 重定向到 `<数据根>/_web_logs/acq-*.log`（无管道），`CREATE_NEW_PROCESS_GROUP` 避免服务端控制台 Ctrl-C 误杀录制。
- **stdin 管道不可用时自动回退**（服务账号/沙箱会 `CreatePipe` 失败）：改为 `stdin=DEVNULL` 且不加 `--stop-on-stdin-eof`，并把 `stdin_failsafe=false` 报给前端，绝不因此让录制起不来。
- 状态：解析日志标记 + 定期扫描会话目录（`os.scandir`），给出 `state / elapsed_s / gb_written / mb_per_s / gb_per_min / session_dir / error`。
- `request_stop()`：写标志文件后**等待进程自行退出**（≤90 s），返回 `still_running`；`kill()` 是**紧急**手段，会在状态里写明"非优雅停止，数据尾部可能不完整"。

### 2.3 端点

| 端点 | 说明 |
|---|---|
| `GET /api/acquisition/configs` | 两份配置的 base_dir/绑定/相机源 + 当前作业状态 + 建议会话名 |
| `GET /api/acquisition/cameras?config=` | 单个配置的相机与绑定 |
| `POST /api/acquisition/cameras/scan` | 扫描 index（录制中 409） |
| `GET /api/acquisition/cameras/preview?index=&width=&height=` | 抓一帧 JPEG（录制中 409；失败 422 带中文原因） |
| `PUT /api/acquisition/bindings` | 校验后写绑定（可选同步另一份配置） |
| `POST /api/acquisition/preflight` | 自检 |
| `POST /api/acquisition/start` \| `stop` \| `kill` | 录制控制 |
| `GET /api/acquisition/status` \| `log` | 实时状态 / 日志尾 |

配置路径被限制在 `scripts/config/**`（非该目录一律 422）。

## 3. 录制前自检与存储预留

| 检查 | 内容 | 状态 |
|---|---|---|
| 配置可加载 | `load_config` 通过（重复 index、arm 冲突等在这里就会失败） | ok/fail |
| 相机自检 | 每个**启用**的相机源按其 index/分辨率/后端抓一帧 | ok/fail |
| 机器人链路 | `pyads` 连接（ams_net_id/port/ip）并读一个符号（只读） | ok/fail |
| 磁盘余量 | `base_dir` 所在卷剩余 ≥ 预估占用 | ok/fail |
| 会话目录 | 目标目录不存在（**同名会写进已有会话目录**，必须换名） | ok/fail |

**存储模型**（本机真实会话实测，2026-09-12；三机位 PNG 1280×720 + 2×640×480 @30 Hz）：

```
test_20260901_144929  146.66 GB / 94263 行 = 1.63 MB/行 -> 2.9 GB/分钟
test_20260828_160624   24.75 GB / 13343 行 = 1.94 MB/行 -> 3.5 GB/分钟
test_20260828_155305   18.89 GB / 10579 行 = 1.87 MB/行 -> 3.4 GB/分钟
⇒ 标定点：整机（三机位）1.8 MB/对齐行 ≈ 3.16 GB/分钟
```

**按配置折算**（同日改进）：写入量与"实际录几路、多少像素"成正比，所以预检按**启用的相机源像素数**折算整机标定值，而不是一律用 3.2 GB/分钟：

| 配置 | 启用相机 | 估算 |
|---|---|---|
| `default.yaml` / `example_acquisition.yaml` | 3 路（1280×720 + 2×640×480） | 1.8 MB/行 → **3.16 GB/分钟** |
| `arm2_only.yaml` | 1 路（1280×720 内窥镜） | 1.08 MB/行 → **1.9 GB/分钟** |
| 无启用相机（测试夹具） | — | 保守取整机默认 3.16 GB/分钟 |

20 分钟预留因此从"一律 64 GB"变成 **整机 63 GB / 仅内窥镜 38 GB**——对只剩几十 GB 的磁盘差别很大。
> 开发中此处曾把"GB/分钟"常量除以 60 当成"GB/小时"，导致 20 分钟只预留 1 GB——**测试断言把量级钉死（60~70 GB）后才暴露**，已在 `probe_acquisition_web.py` 固化。

## 4. 录制期间的设备锁

| 操作 | 录制中 | 理由 |
|---|---|---|
| 相机扫描 / 抓帧预览 | **409 拒绝** | 相机被采集进程独占 |
| 修改相机绑定 | **409 拒绝** | 正在使用这些设备 |
| 再次开始录制 | **409 拒绝** | 一套相机只能录一路 |
| 切换数据目录 | **409 拒绝** | 日志/缓存路径绑定旧根 |
| 流水线（验证/构建/导出视频） | **409 + 警告**，`?force=1` 可继续 | 抢磁盘与 CPU，可能影响录制帧率 |

### 9.4 沙箱发现（影响"谁来验证"）

受限模式（workspace-write）下 **Windows 不向进程暴露 UVC 相机**：所有 index 在 dshow/msmf/any 三种后端下都打不开（MSMF 报 `Camera index out of range`），放宽权限后 index 0/1 立刻可用。因此：

- 代理侧排查相机时需一次性放宽权限（本记录即如此取得）。

### 9.5 真机首录失败定位与修复（"已写 0 GB"的真正原因）

**症状**（用户首录）：面板显示 `recording · 22.9s · 已写 0 GB · 0 MB/s`；`session.json` 里
`camera_arm_2` **0 帧**、`worker_exit_codes: {camera_arm_2: 1}`；采集日志只有
`did not signal ready within 20.0s (camera index 0 not opening)`，**worker 一个字都没输出**。

**定位过程**（逐步排除，都用可复现探针）：

| 实验 | 结果 | 结论 |
|---|---|---|
| 直接跑采集 CLI（shell 启动） | 3 s ready、319 帧 | 相机本身没问题 |
| 单独跑 worker（父进程式 argv/管道） | 4 个变体全 OK | 不是 argv/管道本身 |
| 先抓帧再启动 worker（3 个变体） | 全 OK | 不是"设备释放延迟" |
| 线程池抓帧（模仿 FastAPI 线程） | 5 个变体全 OK | 不是线程/COM 问题 |
| **故意不释放 capture 句柄** | worker 打不开（L1），释放后恢复（L2） | 确认"设备被占用 → worker 静默卡死"这一**故障模式** |
| 二分 Popen 参数 S1–S5 | **仅 S5（带 `--stop-on-stdin-eof`）失败**，两次复现 | 锁定触发条件 |

**真因**：Web 服务用 `stdin=PIPE` 启动采集进程（stdin EOF 兜底），而 `--stop-on-stdin-eof`
让采集进程起线程**读取该 stdin 管道**；相机 worker 默认**继承**这个管道，于是在相机初始化
阶段卡死——既不打开设备也不产生输出（日志还被块缓冲写进"父进程要等到停止才读"的管道，双重丢失）。

**修复**（`usb_camera_process.py` + `usb_camera_worker.py`）：

1. **worker `stdin=DEVNULL`**（根治）：worker 从不读 stdin，绝不继承别人的管道。
2. **worker 输出写文件** `<out_dir>/worker.log`，不再用管道；父进程在就绪超时/退出时把日志末段
   转进采集日志并附在异常信息里（不再出现"worker produced no output"这种无从下手的报错）。
3. **打开相机改为有界重试**（`--open-attempts`，默认 20×1 s；父进程按
   `ready_timeout - warmup - 2` 传预算，确保重试窗口落在父进程超时之内）。
4. 打开前先打 `Opening camera N (attempt i/n)` —— 卡在驱动里也能看出卡在哪一步。
5. Web 侧：状态显示**每路相机帧数**、新增**告警行**（未就绪/打不开/进程异常退出/运行错误），
   **小于 1 GB 用 MB 显示**（"已写 0 GB"本身就是误导）。

**修复后真机实测（arm2 内窥镜 + PLC）**：


  ① **子进程绝不继承 stdin/stdout 管道**（除非确实要通信用），一律 `DEVNULL` 或文件；
  ② 关键 `open` 要**有界重试 + 打开前打点**；
  ③ 无硬件测试**测不出**这类问题——真机第一次跑就一次性暴露三个（单次打开、日志丢失、状态不透明）。

## 10. 会话删除与回收站（2026-09-12，用户需求）

`src/vlgp/web/session_admin.py` + 侧栏会话行的 `×` 按钮 + 「数据目录 → 回收站」。

**为什么默认不是直接删**：一个会话就是 1–150 GB 的**原始采集数据**，没有机器人就得重新录，所以默认走
**同盘移动**到 `<数据根>/_trash/<会话名>_<时间戳>`：

* 同盘 rename → 150 GB 也是瞬间完成，且**可恢复**；
* `_` 开头 → 不会出现在会话列表里（`list_sessions` 已跳过）；
* 真正释放空间的是「**清空回收站**」（二次确认），或用「永久删除」当场释放。

**删除时一并处理**：该会话的预览缓存目录（否则会变成"失效缓存"垃圾）、对齐表缓存条目。
**前置检查（拒绝时给出原因）**：会话名/路径校验（不可能越出数据根）、需 `confirm=true`、
录制中禁止删除、流水线任务运行中禁止删除、该会话正在生成对齐表时禁止删除。

**端点**：

| 端点 | 说明 |
|---|---|
| `GET /api/sessions/{name}/delete-preview` | 文件数/大小/行数/相机/对齐表/评审状态（删除确认框的内容） |
| `POST /api/sessions/{name}/delete?mode=trash\|permanent&confirm=1` | 默认 trash（可恢复），permanent 立即释放 |
| `GET /api/trash` | 回收站条目 + 各自大小 + 合计 |
| `POST /api/trash/restore` | 还原（目标已存在则拒绝，不覆盖） |
| `POST /api/trash/empty` | 清空（需 confirm，这一步才释放空间） |

**前端流程**：会话行 `×` → 第一个对话框列出大小/文件数/相机/评审状态/IN-OUT → 第二个对话框明确二选一
（"确定"=永久删除，"取消"=移入回收站）→ 右下角 toast 提示结果；删掉当前选中的会话会同步清空视图。
`_trash` 与缓存块并列在「数据目录」弹窗里，可逐条恢复或一键清空。

**测试**：`scripts/test/probes/probe_session_delete.py`（合成夹具根，26 项）——确认缺失 422、
trash 后可恢复且缓存被清、恢复不覆盖同名、`_trash` 不被当作会话、未知会话 404、未知模式 422、
**录制中删除被拒 409**、永久删除真删、清空需 confirm。

## 11. 顺带修掉的停止竞态（同日的删除探针挖出来的）

现象：**启动后 1 秒内点停止**（探针的守卫用例正好是这种节奏）时，采集进程**永远不停**，一直录到被
强制结束（实测卡了 80+ 秒）。

原因：`StopSignal.arm()` 原本**无条件删除已存在的停止标志文件**（本意清掉上一次运行的残留），而 Web 的
停止请求正好在采集进程刚起来、还没 arm 时落地 → 标志被当作陈旧文件删掉 → 再也等不到。

修复（双保险）：

1. `stop_signal.arm()` 只在文件**超过 60 秒未更新**时才删；刚创建的是**活的停止请求**，保留并立即生效；
2. Web 的 `request_stop()` **先等采集打出 `=== ACQ RECORDING STARTED`**（监听在此之前已 armed）再写标志，
   从根本避开窗口；返回里带 `started_marker_seen` 便于诊断；
3. 任务结束后服务端清掉该 job 的标志文件（`var/web_acq/*.stop` 不再堆积）。
