## 摘要

本项目面向机器人辅助手术的 **Vision-Language-Guided Procedure (VLGP)** 研究，构建一套多模态数据采集平台，同步记录三路 USB 相机视频与 TwinCAT ADS 机器人运动学数据。当前阶段已完成：

1. **多进程采集框架**：每个相机独立 OS 进程，稳定支持 5 分钟以上连续录制。
2. **硬件能力摸查**：确认 arm_1 / arm_3 相机物理上限约 22.5 fps，arm_2 内窥镜可达 1280×720@60 fps。
3. **跨模态时间对齐**：以 PLC 时间轴为统一参考，实现视频帧与机器人位姿的亚毫秒级对齐（误差 < 1 ms）。
4. **代码库精简**：删除 20+ 个旧脚本、测试重复项与临时文件，释放约 350 MB 空间，关键文件结构已更新。
5. **SRT-H 数据构建方案**：分析 SRT-H 论文源码，确定 4 臂 40 维动作空间、30 Hz 控制频率、触针/抓针/缝合任务的数据格式。
6. **DAgger 收集流程**：制定基于 GUI 按钮纠正的在线恢复数据采集方案。

## 1. 项目目标与研究意义

### 1.1 核心目标

构建面向机器人辅助手术的高质量多模态数据集，为 VLGP 模型提供：

- **视觉输入**：内窥镜主视野（arm_2，高分辨率）+ 双臂手腕相机（arm_1 / arm_3，低分辨率）
- **运动学监督**：通过 TwinCAT ADS 从 Beckhoff PLC 实时读取机器人末端位姿、关节角、器械状态
- **时间基准**：为后续跨模态对齐、动作预测、视觉-语言指令跟随提供可靠的时间对齐基础

### 1.2 技术挑战

| 挑战 | 影响 | 当前状态 |
|---|---|---|
| 多 USB 相机在 Windows DirectShow 下冲突 | 难以同时打开多个相同相机 | 已用独立进程 + 不同分辨率/FOURCC 解决 |
| 相机与 PLC 时钟不同源 | 跨模态时间对齐困难 | 已用事后线性漂移模型 + 最近邻对齐解决 |
| TwinCAT 1 kHz 目标未达成 | 运动学时间分辨率受限 | Python/ADS 端约 320–650 Hz，需确认 PLC 侧是否为瓶颈 |
| 三路相机帧率不一致 | 多视图样本不同步 | 已提出三种对齐策略并验证策略一 |

## 2. 系统架构

```text
┌─────────────────────────────────────────────────────────────┐
│                    AcquisitionSession                       │
│  - host_realtime 统一时钟（time.time_ns）                    │
│  - 共享样本队列 + 主 writer 线程                             │
│  - Ctrl-C 优雅停止 + session.json 元数据                     │
└─────────────────────────────────────────────────────────────┘
        │ registers              │ consumes
        ▼                        ▼
┌──────────────┐        ┌──────────────────┐
│  DataSource  │        │   Disk writers   │
│  (独立线程/进程) │──────▶│  per source CSV  │
└──────────────┘        └──────────────────┘
        │
        ├── process_camera: camera_arm_1, camera_arm_2, camera_arm_3
        │   └── 每个相机一个独立 OS 进程，避免 Windows DirectShow 冲突
        │
        └── twincat: robot_pose
            └── 通过 pyads 读取 PLC 符号，支持 multi-connection 与 output_all_arms
```

### 2.1 数据流

1. 各数据源在独立线程/进程中采集，附带统一 PC 时间戳。
2. 进程相机在子进程内直接落盘；TwinCAT 数据由 Session 主 writer 写入 CSV。
3. 录制结束后，使用 `verify_alignment.py` 估计 PLC-PC 时钟漂移模型。
4. 使用 `unify_alignment.py` 生成以机器人位姿为锚点的统一对齐表。

### 3.1 新相机 cam1 帧率特性详测（2026-08-05/06）

对新接入相机（当前 index 1，640×480 MJPG）做了系统性测试：18 组「曝光 × FPS × 后端」扫描、dshow 离散模式映射（11 档）、60 秒软件抽取验证、MSMF 高优先级专项测试。

**各方案对比**：

| 方案 | 实际 FPS | 帧间隔 std | 最大间隔 | 结论 |
|---|---|---|---|---|
| dshow 原生（不设 FPS） | 64 或 120（**每次启动不确定**） | 2.2–5.9 ms | — | 不能当固定帧率用；“64 fps 怪数值”的来源 |
| dshow + 设置任意 FPS | **31.5**（所有档位都映射到同一模式） | **~1.0 ms** | ~35 ms | 最均匀，但数值不是 30 |
| MSMF + 任意 FPS（含 60） | ~30.1（封顶，**不可能 60**） | ~6.5 ms | ~66 ms | ~1% 帧规律跳拍（~64 ms 间隔），高精度定时器/高优先级无法改善 |
| **dshow 原生 + 软件网格抽帧到 30** | **30.01** | 4.0 ms | 48.5 ms | 唯一精确 30 的方案 |
| **dshow 原生 + 软件网格抽帧到 60** | **60.01** | 3.3 ms | 32.5 ms | 唯一精确 60 的方案 |

**其他发现**：

- 采集 worker 固定曝光（`usb_camera_worker.py` 的 `AUTO_EXPOSURE=0.25, EXPOSURE=-6`）能解除自动曝光对帧率的限制，session `test_20260806_203701` 中相机实测跑到 ~64 fps 且 std 仅 2.18 ms。
- MSMF 已验证支持多相机同时采集（cam0+cam1 同采均 ~30 fps，无读取失败），可作为 dshow 多相机冲突时的备选，但需接受 ~1% 的 ~64 ms 跳帧与 30 fps 封顶。
- `fps: null` 时 worker 不再触碰 `CAP_PROP_FPS`（已修复）；写入配置的 `fps` 值会被 dshow 映射到 31.5 fps 模式，名义帧率与实际不符。

**推荐用法**：

- 要精确 30.00 / 60.00 fps：dshow 原生流 + 软件网格抽帧（建议在 `usb_camera_worker.py` 的 capture loop 实现 `target_fps` 抽帧器，保留真实 PC 时间戳）。
- 只要接近 30 且最均匀：dshow + `fps: 30`（实际 31.5 fps，std ~1 ms）。
- 多相机冲突备选：MSMF（30.1 fps，接受周期性跳帧）。

**重要修正（2026-08-07）**：用户通过 `preview_single_camera.bat` 发现该相机可稳定 60 fps，复核后确认**属实**。关键在于 **OpenCV 属性设置顺序**：preview 脚本的顺序是 `BUFFERSIZE → 宽 → 高 → FPS → FOURCC`（FPS 在 FOURCC **之前**），此顺序下：

| 配置（dshow，预览顺序） | 实际 FPS | std | max |
|---|---|---|---|
| 1280×720, fps=30 或 60 | **60.1** | 3.2 ms | 33 ms |
| 640×480, fps=30 或 60 | 64.1 | 2.2 ms | 19 ms |

**target_fps 软件抽帧器与 PNG 写盘（2026-08-07）**：

- `usb_camera_worker.py` 新增 `--target-fps`：相机跑原生高速流，capture loop 按虚拟时间网格保留真实帧（真实 PC 时间戳），输出精确帧率。`fps`（驱动模式选择）与 `target_fps`（输出速率）独立，可同时设置。

## 6. 多模态时间对齐策略分析

### 6.1 问题背景

采集系统同时记录：
- **视觉数据**：三路 USB 相机，帧率 22–30 fps（离散帧，不可插值）。
- **运动学数据**：TwinCAT ADS 位姿，实际约 312 Hz（连续信号，可插值）。

核心矛盾：**图像是离散采样的，无法在不引入伪影的情况下插值出中间帧；而机械臂位姿是连续信号，可以线性插值或 SLERP 插值。** 因此严格意义上的“零误差同步”不可能实现，只能在不同策略之间做取舍。

### 6.2 策略一：以机器人为基准，取三相机最近帧

**做法**：对每个机器人位姿样本，分别在三路相机中找时间最近的帧，把时间差作为误差列保留。当前 `unify_alignment.py` 采用此策略。

**优点**：
- 保留最高频率的机器人动作信息（不丢失 312 Hz 动作细节）。
- 实现简单，每个机器人时刻都有视觉观测。
- 便于训练“动作 → 下一时刻动作/图像”的模型。

**缺点**：
- 三张图像之间存在时间差（arm_1/arm_3 约 ±11 ms，arm_2 约 ±8 ms）。
- 快速运动场景下，三张图可能拍到机械臂不同空间位置。

**当前实测结果**（`test_20260803_104724`）：

| 相机 | 均值 | 标准差 | 最大值 | 中位数 | 95% 分位 |
|------|------|--------|--------|--------|----------|
| camera_arm_1 | 11.38 ms | 6.78 ms | 24.87 ms | 11.09 ms | 22.57 ms |
| camera_arm_2 | 8.35 ms | 4.82 ms | 18.47 ms | 8.49 ms | 15.86 ms |
| camera_arm_3 | 11.40 ms | 6.77 ms | 24.52 ms | 11.13 ms | 22.55 ms |

**改进方法**：设置误差阈值过滤，只保留三相机误差均小于阈值的样本：

```python
MAX_ERRORS = {
    'camera_arm_1': 10.0,  # ms
    'camera_arm_2': 8.0,
    'camera_arm_3': 10.0,
}
valid = df[
    (df['camera_arm_1_alignment_error_ms'] < MAX_ERRORS['camera_arm_1']) &
    (df['camera_arm_2_alignment_error_ms'] < MAX_ERRORS['camera_arm_2']) &
    (df['camera_arm_3_alignment_error_ms'] < MAX_ERRORS['camera_arm_3'])
]
```

### 6.3 策略二：以某一相机为基准，插值机器人位姿

**做法**：选择 arm_2（30 fps，最稳定）作为主时间轴。对每个 arm_2 帧时刻：
- 找 arm_1、arm_3 的最近帧；
- 用线性插值（位置）+ SLERP（姿态四元数）得到该精确时刻的机器人位姿。

**优点**：
- 三张图像真正“接近同一时刻”。
- 机器人位姿误差可以做得非常小（< 1 ms）。

**缺点**：
- 数据频率被限制在主相机的帧率（如 30 Hz）。
- 需要位姿插值，要求机器人运动平滑；若存在抖动或急停，插值可能失真。

**适用场景**：三维重建、多视角一致性检测等更关心“某一时刻三视角图像 + 该时刻位姿”的任务。

**实现状态（2026-08-05）**：已实现为 `scripts/tools/align_camera_anchor.py`，详见 6.6 节。

### 6.4 策略三：多时间尺度对齐

**做法**：
- **高频分支**：机器人位姿保持 312 Hz，用于精细动作建模。
- **低频同步分支**：每隔 33 ms（对应 arm_2 帧率）创建一个“同步帧”，包含三相机最近帧 + 插值位姿。

**优点**：既保留高频机器人信息，又有严格同步的多视图样本。

**缺点**：数据存储和读取逻辑更复杂，需要维护两个时间索引。

### 6.5 当前推荐方案

推荐 **策略一 + 严格误差过滤**，原因：

1. 机器人位姿频率远高于相机，以机器人为基准不会丢失动作细节。
2. 8–11 ms 的图像时间差远小于单帧周期（33–44 ms），对大多数视觉-语言-动作模型影响有限。
3. 实现和维护成本低，便于快速迭代。

如果后续实验发现三图不同步严重影响模型性能，再引入 **策略二** 生成一个 30 Hz 的严格同步子集进行对比实验。

### 6.6 策略二实现：相机锚点 30 Hz + 位姿插值（2026-08-05）

**工具**：`scripts/tools/align_camera_anchor.py`

**做法**：

1. 用 TwinCAT 双时间戳拟合 `PLC_time = k * PC_time + b` 线性漂移模型，把三路相机的 PC 时间戳映射到 PLC 时间轴。
2. 以 `camera_arm_2`（30 fps 内窥镜）的每一帧时刻 `t` 为锚点。
3. arm_1 / arm_3 取最近帧并记录对齐误差；超出相机活跃区间的样本标记 `in_range=False`。
4. 四条臂的位姿在 `t` 时刻插值：位置 LERP、四元数 SLERP（先做符号连续性处理）、`gripper_angle` / `gripper_signal` 线性插值、`instrument_type` / `energy_instrument_status` 取最近样本；可选 `--include-joints` 同时插值 12 个关节角。
5. 同时兼容多臂布局（`robot_pose/robot_pose_arm<N>/twincat_poses.csv`）和旧单臂布局（`robot_pose/twincat_poses.csv`）。

**用法**：

```bash
python scripts/tools/align_camera_anchor.py --session sessions/<session_name>
# 输出 <session>/camera_anchor_alignment/camera_anchor_alignment.csv
#      <session>/camera_anchor_alignment/camera_anchor_alignment_valid.csv
```

**验证结果**（`sessions/test_20260803_104724`，单臂旧数据）：

| 指标 | 数值 |
|---|---|
| 锚点帧（arm_2） | 2,380 |
| 位姿插值覆盖率 | 2,379（100.0%） |
| 位姿 + 三相机均在有效区间 | 2,228（93.6%） |
| PLC-PC 漂移模型残差 | std 0.276 ms，max 5.408 ms |
| arm_1 最近帧误差 | mean 11.37 ms，p95 22.73 ms（≈22.5 fps 帧周期） |
| arm_3 最近帧误差 | mean 11.35 ms，p95 22.45 ms |
| 插值位置步长 | mean 0.38，p95 1.37，max 2.50（无跳变） |
| 插值四元数模长 | 恒为 1.000000 |

**结论**：策略二已可用。其输出的一行 = 某一时刻三路图像 + 四条臂该时刻的插值位姿，正好对应 SRT-H 低层 policy 的样本单元（当前观测 + 该时刻起的动作序列）。后续只需在此基础上做动作空间转换（hybrid-relative delta + 6D 旋转 + jaw）和 30 Hz 重采样即可生成训练样本。arm_1/arm_3 的 ~11 ms 最近帧误差来自 22.5 fps 物理上限；若手腕相机换为 30 fps（如 cam1 的 MSMF 方案），该误差可进一步降低，并可叠加误差阈值过滤。

## 11. 数据自主标注的讨论与规划

### 11.1 自主标注是否必要？

采集框架本身解决的是「如何稳定、精确地记录多模态数据」问题。但 VLGP（Vision-Language-Guided Procedure）研究需要的不只是原始信号，而是**可训练的（视觉，语言，动作）三元组**。因此：

- 如果目标是「采集与对齐框架」论文：自主标注可作为 downstream application 或 future work，不必作为核心贡献。
- 如果目标是「构建 VLGP 手术机器人数据集」或「端到端 VLGP 系统」：自主标注是必需的，甚至是核心研究问题之一。

### 11.2 最可行的自动标注方向

基于当前已采集的数据，建议按以下优先级推进：

#### 阶段 1：基于运动学状态的自动标注（已具备数据）

利用 TwinCAT 返回的位姿、关节角、器械类型，自动提取：

| 标注类型 | 计算方法 | 用途 |
|---|---|---|
| 器械运动事件 | 末端速度/加速度峰值 | 「插入」「回撤」「夹取」等 |
| 运动阶段分割 | 位姿轨迹聚类 / 变点检测 | 自动划分手术阶段 |
| 静止/运动区间 | 位姿变化阈值 | 标注 idle / active 片段 |
| 工具切换事件 | `instrument_types` 变化 | 工具使用序列 |
| 工作空间区域 | 3D 末端位置聚类 | 视野左/右侧操作 |

#### 阶段 2：基于视觉的自动标注

| 标注类型 | 方法 | 用途 |
|---|---|---|
| 器械检测/分割 | 预训练手术器械检测模型 | bounding box / mask |
| 关键帧提取 | 根据运动学事件定位视频帧 | 动作起止帧 |
| 异常检测 | 视觉与运动学不一致 | 数据清洗 |

#### 阶段 3：语言标注生成（VLGP 核心）

| 方向 | 示例 | 难度 |
|---|---|---|
| 模板化语言生成 | 「使用抓钳进行快速移动」 | 低 |
| 手术步骤描述生成 | 「将抓钳移动到左侧，夹持组织」 | 高 |
| 动作-语言对齐 | 把自然语言指令映射到视频片段和位姿序列 | 中高 |

### 11.3 风险与边界

- **临床有效性**：自动标注需经医生或机器人工程师小规模校验，低置信度样本送人工确认。
- **Scope 控制**：建议先聚焦「基于运动学的阶段分割」一个点，避免同时铺开视觉分割、大语言模型、端到端训练。
- **隐私与伦理**：手术数据需 IRB/伦理审批、脱敏与访问控制。

### 11.4 与老师讨论时可提出的问题

1. 自主标注应作为独立研究方向，还是采集系统的 downstream application？
2. 模板化生成 vs 视觉-语言大模型生成，哪个更适合当前阶段？
3. 如何在没有大量人工标注的情况下评估自动标注质量？
4. 手术机器人自动标注更适合投 ICRA、MICCAI 还是 CVPR/ACL？

## 12. 视频片段与动作序列的对齐

### 12.1 问题重述

如果无法做到「每一帧图像 ↔ 每一个机器人状态」的精确一一对齐，是否可以改为：

> 传入一段视频片段（连续 N 帧图像）和对应时间窗口内的机器人动作状态序列，对这两个序列进行对齐？

### 12.2 结论：可以，且在很多场景下更合理

**答案是肯定的。** 这种「序列对序列」的对齐不仅可行，而且在 VLGP 研究中往往比逐帧对齐更自然：

- 人类的手术操作指令通常是**时间段级别**的（例如「夹持组织 3 秒」），而不是单帧级别的。
- 视频帧率和机器人状态频率差异巨大（22–30 fps vs 312 Hz），强行逐帧对齐会造成大量插值或丢弃。
- 视频片段包含时序上下文，对动作识别更有帮助。

### 12.3 技术路线

#### 12.3.1 传统方法

| 方法 | 核心思想 | 适用场景 |
|---|---|---|
| **Dynamic Time Warping (DTW)** | 寻找两条序列间的最优非线性时间弯曲 | 视频特征序列与状态序列长度不同、采样率不同 |
| **Canonical Correlation Analysis (CCA)** | 学习两个模态特征子空间的线性映射 | 需要训练数据但无显式时间标签 |
| **Cross-Correlation** | 计算两个时序信号的互相关峰值 | 信号有明显同步事件 |
| **HMM / CTC** | 用隐状态建模动作阶段，进行软对齐 | 有阶段标签或动作类别 |

#### 12.3.2 深度学习方法

| 方法 | 核心思想 | 代表工作 |
|---|---|---|
| **Temporal Cycle Consistency (TCC)** | 学习视频帧之间的循环一致性表征 | CVPR 2019 |
| **Time-Contrastive Networks (TCN)** | 同一时刻不同视角为正样本，不同时刻为负样本 | ICRA 2018 |
| **LAV (Local Alignment Verbs)** | 视频片段与自然语言指令的局部时间对齐 | CVPR |
| **Contrastive Learning** | 拉近同步的视频片段和动作序列，推远不同步的 | 通用框架 |
| **Transformer Cross-Attention** | 用交叉注意力学习视频帧与状态序列的软对齐 | 当前主流 |

### 12.4 在本项目中的实现思路

结合现有数据，可按以下步骤尝试：

1. **特征提取**
   - 视频片段：用预训练 CNN（ResNet、Video Swin、TimeSformer）提取帧级或片段级特征。
   - 动作序列：用位姿速度、关节角变化、器械状态等构造状态特征向量。

2. **时序建模**
   - 对视频特征序列用 1D-CNN 或 Transformer encoder 建模局部时序。
   - 对动作状态序列用相同结构编码。

3. **对齐损失**
   - **对比损失**：同一操作片段的视频特征与动作特征拉近，不同操作推远。
   - **DTW 损失**：最小化两个特征序列的最优对齐距离。
   - **阶段分类损失**：如果已知阶段标签，用交叉熵约束对齐。

4. **输出形式**
   - 软对齐矩阵：视频第 i 帧与动作第 j 步的对应概率。
   - 粗粒度对应：视频片段 ↔ 动作子序列。
   - 语言描述生成：基于对齐结果生成「在这段时间内，机器人执行了 XX 动作」。

### 12.5 优势与挑战

**优势**：
- 不要求精确的帧级时间戳对应。
- 自然处理不同采样率。
- 更符合 VLGP 中语言指令的时间粒度。
- 可利用大量未配对的多模态数据进行自监督预训练。

**挑战**：
- **相似动作歧义**：例如反复「夹持-松开」容易造成对齐混淆。
- **时间粒度选择**：片段太短则失去上下文，太长则对齐模糊。
- **缺乏 ground truth**：评估对齐质量需要人工标注或设计代理指标。
- **计算成本**：视频特征提取和序列比对计算量较大。

### 12.6 与当前采集框架的结合

当前系统已经为这种片段级对齐提供了良好基础：

- `unify_alignment.py` 已经给出了「某段机器人位姿 ↔ 某段视频帧」的粗对应。
- `analyze_session.py` 可以输出时间覆盖率和同步质量，帮助选择高质量片段。
- 下一步可以基于 `unified_alignment_valid.csv` 中的有效窗口，训练一个片段级对齐模型。

### 12.7 建议的研究问题

如果要把这个方向作为论文贡献，可以定位成：

> *"Weakly-supervised temporal alignment between video clips and robot state sequences for surgical procedure understanding"*

或

> *"Learning coarse-to-fine cross-modal alignment for vision-language-guided surgical robots"*

## 13. SRT-H 数据格式与我们的数据构建方案

### 13.1 SRT-H 数据格式总结

根据 SRT-H 论文源码分析，其训练数据格式如下：

**视觉输入**：
- 立体内窥镜左目：960×540，训练时 resize 到 224×224
- 左/右手腕相机：640×480，训练时 resize 到 224×224
- 统一 30 fps
- HL policy：当前帧 + 过去 4 帧，每帧间隔 1 秒
- LL policy：当前时刻三路图像

**机器人动作**：
- 双臂 PSM1 + PSM2
- 位置 `position.x/y/z` + 四元数 `orientation.x/y/z/w`
- 动作表示：hybrid-relative（平移相对内窥镜尖端，旋转相对末端执行器）
- 动作空间：20 维 = 每臂 3（平移）+ 6（6D 旋转）+ 1（夹爪）
- Action chunking：k=60（30 fps × 2 秒）

**语言标注**：
- Task instruction：如 `"grabbing gallbladder"`, `"clipping first clip left tube"`
- Corrective instruction：如 `"move left arm to the right"`
- Correction flag：是否处于 recovery 模式

**数据规模**：
- 约 16,000 条 demonstrations
- 34 个 ex-vivo 猪胆囊
- 17 个任务（抓胆囊 + 12 个 clip + 4 个 cut）

### 13.2 我们当前系统与 SRT-H 的映射

| 项目 | SRT-H | 我们当前系统 |
|---|---|---|
| 相机配置 | 内窥镜 + 2 手腕相机 | arm_2 内窥镜 + arm_1/arm_3 手腕相机 |
| 臂数 | 2 条手术臂 | 4 条臂（arm_1/arm_3 常用手，arm_2 内窥镜，arm_4 非常用手） |
| 帧率 | 统一 30 fps | arm_2 30 fps，arm_1/arm_3 22.5 fps（后续升级） |
| 动作表示 | hybrid-relative delta | 当前为绝对位姿，需转换 |
| 语言标注 | 任务标注 + 自动生成纠正指令 | 当前无，需构建 |

### 13.3 我们的数据构建方案

#### 13.3.1 动作空间：统一 4 臂 + activation mask

推荐采用统一 40 维动作空间：

```text
总维度 = 4 臂 × (3 delta_pos + 6 delta_rot_6d + 1 jaw) = 40 维
arm_active_mask = [arm_1, arm_2, arm_3, arm_4]  # bool
```

不同任务的激活示例：

| 任务 | arm_1 | arm_2 | arm_3 | arm_4 |
|---|---|---|---|---|
| 触针 | 1 | 0 | 0 | 1 |
| 抓针 | 1 | 0 | 0 | 1 |
| 自主缝合 | 1 | 0 | 1 | 1 |
| 内窥镜调整 | 0 | 1 | 0 | 0 |

#### 13.3.2 控制频率：30 Hz

选择 30 Hz，处理方式：
- arm_2 内窥镜：原生 30 fps，直接使用
- arm_1 / arm_3 手腕相机：22.5 fps → 30 Hz，短期采用**最近邻帧重复**
- 机器人位姿：312 Hz → 30 Hz，下采样/插值

> 说明：wrist camera 物理上限为 22.5 fps，30 Hz 通过最近邻上采样实现。设备升级后将统一为原生 30 fps。

#### 13.3.3 三个简单任务的数据格式

每个 demonstration 保存为 HDF5 / zarr：

```text
demo_0000.hdf5
├── observations/
│   ├── endoscope          # [T, 224, 224, 3]  arm_2
│   ├── wrist_left         # [T, 224, 224, 3]  arm_1
│   └── wrist_right        # [T, 224, 224, 3]  arm_3
├── actions/
│   ├── delta_pos          # [T, 4, 3]
│   ├── delta_rot_6d       # [T, 4, 6]
│   └── jaw                # [T, 4, 1]
├── arm_active_mask        # [T, 4] bool
├── language/
│   ├── task_instruction   # str
│   ├── corrective_instruction  # str or ""
│   └── correction_flag    # bool
└── metadata/
    ├── timestamps_pc      # [T]
    ├── timestamps_plc     # [T]
    └── alignment_error_ms # [T]
```

#### 13.3.4 任务-specific 设计

**触针（Needle Touching）**：
- 主要臂：arm_1 或 arm_3
- 辅助臂：arm_4（固定/托底）
- 语言标签：`"approach needle"`, `"touch needle"`, `"retract from needle"`

**抓针（Needle Grasping）**：
- 主要臂：arm_1 或 arm_3
- 关键事件：接近 → 张爪 → 夹紧 → 提起
- 语言标签：`"approach needle"`, `"open gripper"`, `"grasp needle"`, `"lift needle"`

**自主缝合（Autonomous Suturing）**：
- 主要臂：arm_1 + arm_3
- 辅助臂：arm_4（拉线/固定组织）
- 建议拆分子任务：
  - `"insert needle through tissue"`
  - `"pull suture thread"`
  - `"prepare first knot"`
  - `"tighten knot"`

#### 13.3.5 SRT-H 分层架构的数据需求

**High-level policy 样本**：
- 输入：endoscope 历史 5 帧（当前 + 过去 4 秒，间隔 1 秒）
- 输出：task_instruction, correction_flag, corrective_instruction
- 预测频率：每 3 秒一次
- 预测偏移：未来 0.5 秒

**Low-level policy 样本**：
- 输入：当前 endoscope + 双 wrist camera + language instruction
- 输出：未来 K 步动作，K=60（2 秒 @ 30 Hz）
- 动作维度：40 维（4 臂）

**纠正指令词汇表（示例）**：

```text
"move left arm to the right"
"move left arm up"
"move left arm towards me"
"move right arm to the left"
"move right arm down"
"open left gripper"
"close left gripper"
"reposition needle"
"pull suture tighter"
```

### 13.5 对齐与模型输入方案（2026-08-08 确认）

**锚点帧率定为 30 Hz**（与 SRT-H LL policy 一致），锚点相机为 arm_2 内窥镜：

1. 以 arm_2 每帧时刻为网格点；arm_1 / arm_3 取最近帧（误差阈值 15 ms 过滤）；四臂位姿 LERP/SLERP 插值到网格时刻（误差 < 1 ms）。
2. 动作标签（LL policy 输出侧）：相邻网格点间，每臂计算 `delta_pos`（镜体系，`scope_position` 差分）+ `delta_rot_6d`（末端系相对旋转取前两列）+ `jaw`（`gripper_angle` 归一化）；四臂 40 维 + `arm_active_mask`；每样本存未来 60 步（2 s）动作 chunk。
3. HL policy 样本：同一条 30 Hz 内窥镜流按 1 s 间隔取 5 帧（t, t-1s, …, t-4s）。
4. episode 结构：`obs/{endoscope,wrist_left,wrist_right}` + `actions.parquet` + `arm_active_mask` + `language.json` + `meta.json`（含对齐误差统计）。

**坐标系与四元数确认（2026-08-16）**：

1. **四元数顺序为 wxyz（scalar-first）**。`scipy.spatial.transform.Rotation.from_quat` 要求 xyzw，`build_srth_dataset.py` 读入 PLC 四元数后必须先重排 `q_xyzw = q[[1, 2, 3, 0]]`；脚本内需带单元自检（恒等旋转 + 已知 90° 旋转）防止回归。
2. **PLC 同时输出两套位姿：机械臂基坐标系 + 镜坐标系**。动作标签（`delta_pos` / `delta_rot_6d`）统一使用**镜坐标系**位姿：与 arm_2 相机锚点同系、内窥镜移动时其他臂的 delta 自动包含自我运动补偿（与 SRT-H 一致）、不受机器人基座摆放影响。基坐标系位姿保留在 `meta.json` / parquet 中，用于工作空间检查与离线可视化。
3. 剩余两项不再依赖外部排期，由数据侧闭环：① 镜系轴向 sanity check（让一臂沿已知方向纯平移，离线验证 delta_pos 符号与轴向，并入端到端试跑）；② `gripper_angle` 量程与方向从已有 session 的 CSV 极值反推。

### 14.1 医生手抖会影响模型学习吗？

**结论：会，但影响程度取决于手抖的性质和数据量。**

#### 14.1.1 小手抖（高频低幅）

- **影响较小**：神经网络具有平均效应，大量 demonstration 中的随机手抖会相互抵消，模型倾向于学习平滑的平均轨迹。
- **甚至有好处**：适当的手抖相当于数据增强，可以提升模型的鲁棒性。

#### 14.1.2 显著抖动 / 修正性微动

- **可能产生负面影响**：
  - 模型可能学会不必要的抖动轨迹
  - 在接近目标点时产生振荡
  - 夹爪开合时机被手抖干扰
- **典型表现**：
  - 预测轨迹 jerk 较大
  - 在目标位置附近反复修正
  - 动作 chunk 中出现高频波动

#### 14.1.3 缓解方法

| 方法 | 做法 | 效果 |
|---|---|---|
| **动作平滑（Low-pass filter）** | 对位姿序列做 Savitzky-Golay 或高斯平滑 | 去除高频手抖 |
| **Delta action 正则化** | 在 loss 中加入动作变化率惩罚 | 鼓励平滑轨迹 |
| **数据增强** | 在训练时添加可控噪声 | 提升泛化性 |
| **增加数据量** | 更多医生/更多 demonstration | 随机手抖自然平均 |
| **Quality filtering** | 用 jerk/平滑度指标过滤低质量 demo | 剔除严重抖动样本 |
| **Diffusion policy / VQ-VAE** | 生成式模型天然学习分布均值 | 自动平滑 |

**具体建议**：
- 在数据预处理阶段对绝对位姿做轻微平滑（窗口 3–5 帧）
- 训练时在 L1 loss 基础上加入动作加速度惩罚
- 对明显异常的 demonstration（如 jerk 超过阈值 3 倍）进行人工复核

### 14.2 错误状态恢复数据需要收集多少？

**结论：不是越多越好，关键是多样性和比例。**

#### 14.2.1 参考比例

| 来源 | 最优数据 | 恢复数据 | 恢复数据比例 |
|---|---|---|---|
| SRT-H | 13,189 条 | 5,167 条 | ~28% |
| 一般模仿学习 | — | — | 10%–30% |
| 简单任务初期 | 50–100 条 | 10–30 条 | ~15%–25% |

#### 14.2.2 比数量更重要的是多样性

对于每个任务，应覆盖主要失败模式：

**触针任务**：
- 针偏左时的恢复
- 针偏右时的恢复
- 针偏高/偏低时的恢复
- 夹爪过早闭合的恢复

**抓针任务**：
- 夹取位置偏斜的恢复
- 未夹住针的恢复
- 夹住但滑脱的恢复

**缝合任务**：
- 针刺入角度错误的恢复
- 线缠绕的恢复
- 打结松动的恢复

#### 14.2.3 更高效的收集方式：DAgger

单纯离线收集 recovery demonstrations 效率不高，更推荐 **DAgger-style** 在线收集：

1. 先用最优数据训练一个 base policy
2. 部署 policy，观察其失败模式
3. 在失败状态下，由医生给出纠正指令
4. 记录（失败状态图像，纠正指令，纠正动作）三元组
5. 用新数据 fine-tune policy
6. 重复 2–5 步

**优点**：
- 只收集 policy 实际会犯的错误，数据利用率高
- 和 SRT-H 的 HL DAgger 思路一致
- 通常 2–3 轮迭代就能看到明显改善

#### 14.2.4 针对你们三个任务的建议

| 任务 | 最优数据 | 恢复数据 | 备注 |
|---|---|---|---|
| 触针 | 50–80 条 | 每条失败模式 5–10 条 | 覆盖 4–6 种偏移方向 |
| 抓针 | 80–120 条 | 每条失败模式 8–12 条 | 重点覆盖滑脱和偏斜 |
| 缝合 | 150–300 条 | 占总数据 20–30% | 失败模式更复杂，需要更多 |

#### 14.2.5 恢复数据的标注要点

每条 recovery demonstration 需要记录：
- **进入失败状态前的 3 秒上下文**（SRT-H 的做法）
- **失败状态的具体类型**（用于分析失败分布）
- **纠正指令**（自然语言）
- **纠正后的动作序列**
- **最终是否恢复成功**

### 14.3 给老师讨论的要点

1. 手抖是否应该被显式过滤？还是让模型自己学习平滑化？
2. 恢复数据的最佳比例是多少？是否需要根据任务难度动态调整？
3. 是否应采用 DAgger 方式在线收集恢复数据，而不是离线录制？
4. 如何定义和分类手术任务的失败模式？
5. 手抖是否可以作为一种数据增强，提升模型对传感器噪声的鲁棒性？

## 15. DAgger 具体操作流程

### 15.1 核心思想

DAgger（Dataset Aggregation）在本项目中的核心思想：

> **先训练一个 base policy，让它在实际任务中犯错；然后由医生在错误状态下给出纠正，把这些（错误状态 + 纠正指令 + 纠正动作）加入数据集，重新训练 policy。**

SRT-H 的论文里把这叫 **HL DAgger**，因为他们主要纠正的是 **High-level policy 的语言输出**，而不是每一帧的低层动作。

### 15.2 整体流程

```text
第 0 轮：收集最优演示数据 D_base
    ↓
训练 base policy π_0（HL + LL）
    ↓
for iteration = 1, 2, 3, ...:
    部署 π_{i-1} 执行任务
    ↓
    policy 进入失败/次优状态
    ↓
    医生给出纠正（语言 + 动作）
    ↓
    记录 D_corr_i
    ↓
    D_i = D_base ∪ D_corr_1 ∪ ... ∪ D_corr_i
    ↓
    在 D_i 上 fine-tune policy 得到 π_i
```

### 15.3 三种纠正方式

#### 15.3.1 方式 A：纯语言纠正（SRT-H 方式）

**流程**：
1. Policy 自主运行
2. 医生观察到失败趋势或失败状态
3. 医生说出纠正指令，如「左臂往右一点」「张开夹爪」
4. 语音转文本后送入 LL policy，替代 HL policy 的指令
5. LL policy 根据纠正指令生成动作
6. 状态恢复后切回 HL policy 自主控制

**优点**：不需要手动操作机器人，数据标注自动（语音转文本）。
**缺点**：需要语音识别系统，词汇表受限。

#### 15.3.2 方式 B：医生 Teleoperation 纠正

**流程**：
1. Policy 运行
2. 医生按下「接管」按钮
3. 医生用手柄/主手 teleoperate 机器人完成恢复
4. 松开接管按钮，policy 恢复自主
5. 事后为恢复段标注纠正语言

**优点**：纠正动作更自然准确，词汇表不限。
**缺点**：医生操作负担重，事后需补充语言标注。

#### 15.3.3 方式 C：GUI 按钮纠正（推荐初期使用）

**流程**：
1. 准备 GUI，显示常用纠正指令按钮：
   - 方向类：「左臂往右」「右臂往左」「左臂上」等
   - 夹爪类：「张开左夹爪」「闭合左夹爪」等
   - 任务类：「重新定位针」「拉紧线」等
2. Policy 运行
3. 医生点击按钮
4. 按钮对应指令送入 LL policy
5. 执行 3–5 秒后自动切回 HL policy

**优点**：无需语音识别，语言标签直接由按钮决定，最容易快速实现。
**缺点**：词汇表受限，不如自然语言灵活。

### 15.4 D_corr 样本格式

```python
{
    "observation_history": {
        "endoscope": [90, 224, 224, 3],      # 失败前 3 秒 @ 30 Hz
        "wrist_left": [90, 224, 224, 3],
        "wrist_right": [90, 224, 224, 3]
    },
    "original_hl_output": {
        "task_instruction": "insert needle",
        "correction_flag": False,
        "corrective_instruction": ""
    },
    "corrective_language": "move left arm to the right",
    "corrective_actions": [90, 40],           # 3 秒 @ 30 Hz，40 维 4 臂动作
    "arm_active_mask": [90, 4],
    "task_name": "suture insertion",
    "failure_mode": "needle_deviated_left",   # 失败模式分类
    "recovery_success": True,
    "operator_id": "doctor_001",
    "timestamp": "..."
}
```

### 15.5 Fine-tune 策略

#### HL Policy Fine-tune

```python
D_merged = D_base ∪ D_corr

train_hl_policy(
    dataset=D_merged,
    learning_rate=1e-6,  # 比 base 训练更小
    epochs=300,
    loss_weights={
        "task_loss": 1.0,
        "correction_flag_loss": 2.0,
        "corrective_instruction_loss": 2.0
    }
)
```

**技巧**：
- 60% 训练样本从 recovery demonstrations 开始
- 加重 correction_flag 和 corrective_instruction 的 loss 权重
- 使用较小学习率，避免遗忘 base 能力

#### LL Policy Fine-tune

```python
train_ll_policy(
    dataset=D_merged
    # 同时包含 task instructions 和 corrective instructions
)
```

### 15.6 迭代计划

| 轮次 | 目标 |
|---|---|
| 第 1 轮 | 覆盖最常见的 3–5 种失败 |
| 第 2 轮 | 覆盖第 1 轮 policy 新暴露的失败 |
| 第 3 轮 | 处理长尾失败模式 |
| 第 4 轮+ | 边际收益递减，视情况停止 |

**停止条件**：
- 成功率达到可接受水平
- 新增纠正数据不再显著改善性能
- 失败模式已充分覆盖

### 15.7 与现有采集框架的结合

#### 需要新增的模块

| 模块 | 作用 |
|---|---|
| `policy_runner.py` | 加载训练好的 policy，实时生成动作 |
| `human_override.py` | 监听医生接管信号（GUI/语音/手柄） |
| `correction_recorder.py` | 记录纠正样本 |
| `failure_detector.py` | 自动检测是否需要纠正（可选，第二阶段） |
| `dagger_scheduler.py` | 管理多轮 DAgger 迭代 |

#### 数据目录结构

```text
├── rollouts/
│   ├── rollout_000/
│   │   ├── observations/
│   │   ├── policy_predictions.csv
│   │   └── robot_states.csv
│   └── corrections/
│       ├── correction_000/
│       │   ├── pre_failure_images/      # 失败前 3 秒

    └── dagger_iter_01.hdf5
```

### 15.8 最小可行版本（第一周验证）

1. **只做一个任务**：抓针
2. **收集 5–10 条恢复数据**
3. **使用 GUI 按钮纠正**：6–8 个方向 + 开闭夹爪
4. **只 fine-tune HL policy**
5. **评估指标**：policy 在相同失败状态下能否自动恢复

### 15.9 关键注意事项

- **安全第一**：机器人必须在安全速度限制下运行，医生可随时急停
- **失败模式多样化**：不要只收集同一种失败的纠正
- **纠正数据比例**：建议控制在 10%–30%，过多会让模型「预期失败」
- **记录医生 ID**：不同医生纠正风格不同，便于分析
- **语言标准化**：尽量使用规范化的纠正指令文本

## 16. PTP 时间同步调研（2026-08-05）

**背景**：当前跨模态对齐采用「PC 软时间戳 + 事后线性漂移校准」，误差 ~1 ms，对 30 Hz 数据足够。若未来需要**精确曝光时刻**（三维重建、多相机严格同步、高速运动分析），可升级到 IEEE 1588 PTP 硬件时间同步。本节为可行性调研结论。

### 16.1 PLC 侧：Beckhoff EL6688

- [EL6688 官方页](https://www.beckhoff.com/en-en/products/i-o/ethercat-terminals/el6xxx-communication/el6688.html)：EtherCAT 端子形态的 IEEE 1588 时钟，支持 PTPv1/v2，经 EtherCAT DC 系统同步，使 TwinCAT 任务时间挂到 PTP 时间域；TwinCAT System Manager 中可选 `SlaveOnly` / `MasterOnly` / `Best Master Clock`。
- 物理规格：12 mm 端子、E-bus 供电、PTP 网口为 10/100 M。
- 价格参考（第三方渠道，波动大）：全新约 $900–2,600（[NEX $972](https://www.nexinstrument.com/el6688)、[PLC Direct $2,594](https://plc-direct.com/products/el6688)），二手/拆机约 $190–900（[eBay ~$189](https://www.ebay.com/itm/185596768016)）。
- **关键前提（最大不确定性）**：EL6688 必须插到**机器人控制器自己的 EtherCAT 总线**上并由其 TwinCAT 工程配置，**绕不开机器人工程师**。需确认：① 控制器是否有可扩展 E-bus 端子排；② 是否允许改 TwinCAT 工程；③ PLC 侧时间如何暴露给采集端。

### 16.2 相机侧：海康 GigE 工业相机 PTP

- 海康机器人 GigE 面阵相机**原生支持 IEEE 1588 PTP v2**：在 MVS 客户端 Transport Layer 参数中启用 IEEE 1588 V2，相机可设 Master/Slave，配合主机端 linuxptp（`ptp4l`）完成同步（[CSDN 实践](https://blog.csdn.net/lovely_yoshino/article/details/139663302)）。帧时间戳经 MVS SDK 的 `MV_FRAME_OUT_INFO_EX.nTimeStamp` 读出，PTP 使能后即在 PTP 时间域。
- GigE Vision 2.0 以 PTP 为多相机同步基础，配合 Action Commands 可做 µs 级软触发（[Basler 说明](https://www.baslerweb.com/en/learning/multi-camera-systems-gige-vision-2.0/)）。
- **USB 接口工业相机不支持 PTP**（[IDS 技术说明](https://cn.ids-imaging.com/techtipp-details/items/ptp_clock_comparison.html)）：现有 USB 腕部相机与采集卡内窥镜均不在 PTP 体系内。
- 价格参考（淘宝在售，含拆机件）：MV-CA050-10GM/GC（500 万像素 IMX250 全局快门，~100 fps 级）约 ¥480–1,300，官方全新约 ¥1,500–3,000；三台腕部相机预算约 ¥5,000–10,000。

### 16.3 PTP 化整体架构

```text
        Grandmaster（三选一）
   A. 某台相机设 Master（最简单，仅相机间同步）
   B. 采集 PC + Intel I210/I226 网卡（ptp4l，Windows 支持差）
   C. PLC 侧 EL6688 设 Master（以 PLC 为基准，与现状一致）
                  │ PTPv2
        ┌─────────┼─────────┐
   GigE相机1  GigE相机2  GigE相机3   （Slave，曝光时刻直接打 PTP 时间戳）
   机器人控制器 E-bus 上的 EL6688（Slave）→ TwinCAT 任务时间挂到 PTP 域
```

采集端改动：相机采集从 OpenCV/DirectShow 换成 MVS SDK / GenICam，直接读帧自带 PTP 时间戳；事后漂移校准可完全省掉。

### 16.4 风险与建议路径

| 风险 | 说明 |
|---|---|
| 机器人工程师配合度 | EL6688 涉及控制器硬件 + TwinCAT 工程，是关键路径 |
| Windows PTP 主机 | linuxptp 在 Linux 成熟；Windows 采集 PC 建议让相机/PLC 当 Master，或配 I210/I226 网卡 |
| 内窥镜无法 PTP 化 | 采集卡→USB 链路不在 PTP 体系；主视野若要曝光时刻需另选 GigE 方案 |
| 必要性 | 当前 ~1 ms 事后校准对 30 Hz 已够；PTP 收益在曝光时刻精度与零校准 |

**建议路径**：

1. 先与机器人工程师确认 EL6688 可行性（关键路径）；
2. 先单买一台海康 GigE 相机（约 ¥1,500）验证 MVS + PTP 采集链路（相机互为 Master/Slave，不依赖 PLC 侧）；
3. 两步验证通过后再决定是否上完整 PTP 体系。

### 17.2 `pack_session.py`：SurgSync 风格打包

**工具**：`scripts/tools/pack_session.py`

```bash
python scripts/tools/pack_session.py --session sessions/<session_name> [--verify]
```

**输出布局**（`packed/<session_name>/`）：

```text
├── video/<camera>.mkv                 # FFV1 level 3，全 I 帧，bit-exact
├── frames/<camera>.parquet            # 每帧时间戳；第 i 行 == 视频第 i 帧
├── robot_pose/robot_pose_arm<N>.parquet
├── session.json                       # 原样拷贝
├── episode_meta.json                  # episode 摘要（task 字段待标注填入）
└── manifest.json                      # 所有文件的 SHA-256
```

**对齐契约（关键设计）**：视频容器不承担时间同步职责。`frames/<camera>.parquet` 的第 i 行对应视频第 i 帧，行内带 PLC 时间轴时间戳；任意帧时刻的机器人关节状态通过对 `robot_pose/*.parquet` 做 LERP/SLERP 插值获得（即 `align_camera_anchor.py` 的做法）。帧↔关节的对齐精度与打包前完全一致。

**验证结果**（`--verify` 全量解码比对 SHA-256）：

| session | 内容 | PNG 原始 | FFV1 mkv | bit-exact |
|---|---|---|---|---|
| test_sync_start | 480p × 517 帧 | ~100 MB | 53.6 MB | ✅ PASS |
| test_cam1_720p_png30 | 720p × 601 帧 | 233 MB | 104.9 MB | ✅ PASS |

压缩率约 45–54%，且**数学无损**（任意帧可逐像素还原，满足训练清晰度要求）。

**实现要点**：conda ffmpeg 的 Windows 构建不支持 glob 输入、concat demuxer 对静态图片有时间戳丢弃问题，因此采用 **OpenCV 解码 PNG → rawvideo BGR24 管道喂给 ffmpeg** 的方式，帧数与像素由管道侧完全控制。ffmpeg 经 `conda install -c conda-forge ffmpeg` 安装，`pyarrow` 用于 parquet。
