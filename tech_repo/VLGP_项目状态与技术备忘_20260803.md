## 摘要

本项目面向机器人辅助手术的 **Vision-Language-Guided Procedure (VLGP)** 研究，构建一套多模态数据采集平台，同步记录三路 USB 相机视频与 TwinCAT ADS 机器人运动学数据。当前阶段已完成：

1. **多进程采集框架**：每个相机独立 OS 进程，稳定支持 5 分钟以上连续录制。
2. **硬件能力摸查**：确认 arm_1 / arm_3 相机物理上限约 22.5 fps，arm_2 内窥镜可达 1280×720@60 fps。
3. **跨模态时间对齐**：以 PLC 时间轴为统一参考，实现视频帧与机器人位姿的亚毫秒级对齐（误差 < 1 ms）。
4. **代码库精简**：删除 20+ 个旧脚本、测试重复项与临时文件，释放约 350 MB 空间，关键文件结构已更新。
5. **SRT-H 数据构建方案**：分析 SRT-H 论文源码，确定 4 臂 40 维动作空间、30 Hz 控制频率、触针/抓针/缝合任务的数据格式。
6. **DAgger 收集流程**：制定基于 GUI 按钮纠正的在线恢复数据采集方案。

## 1. 项目目标与研究意义

### 1.1 核心目标

构建面向机器人辅助手术的高质量多模态数据集，为 VLGP 模型提供：

- **视觉输入**：内窥镜主视野（arm_2，高分辨率）+ 双臂手腕相机（arm_1 / arm_3，低分辨率）
- **运动学监督**：通过 TwinCAT ADS 从 Beckhoff PLC 实时读取机器人末端位姿、关节角、器械状态
- **时间基准**：为后续跨模态对齐、动作预测、视觉-语言指令跟随提供可靠的时间对齐基础

### 1.2 技术挑战

| 挑战 | 影响 | 当前状态 |
|---|---|---|
| 多 USB 相机在 Windows DirectShow 下冲突 | 难以同时打开多个相同相机 | 已用独立进程 + 不同分辨率/FOURCC 解决 |
| 相机与 PLC 时钟不同源 | 跨模态时间对齐困难 | 已用事后线性漂移模型 + 最近邻对齐解决 |
| TwinCAT 1 kHz 目标未达成 | 运动学时间分辨率受限 | Python/ADS 端约 320–650 Hz，需确认 PLC 侧是否为瓶颈 |
| 三路相机帧率不一致 | 多视图样本不同步 | 已提出三种对齐策略并验证策略一 |

## 2. 系统架构

```text
┌─────────────────────────────────────────────────────────────┐
│                    AcquisitionSession                       │
│  - host_realtime 统一时钟（time.time_ns）                    │
│  - 共享样本队列 + 主 writer 线程                             │
│  - Ctrl-C 优雅停止 + session.json 元数据                     │
└─────────────────────────────────────────────────────────────┘
        │ registers              │ consumes
        ▼                        ▼
┌──────────────┐        ┌──────────────────┐
│  DataSource  │        │   Disk writers   │
│  (独立线程/进程) │──────▶│  per source CSV  │
└──────────────┘        └──────────────────┘
        │
        ├── process_camera: camera_arm_1, camera_arm_2, camera_arm_3
        │   └── 每个相机一个独立 OS 进程，避免 Windows DirectShow 冲突
        │
        └── twincat: robot_pose
            └── 通过 pyads 读取 PLC 符号，支持 multi-connection 与 output_all_arms
```

### 2.1 数据流

1. 各数据源在独立线程/进程中采集，附带统一 PC 时间戳。
2. 进程相机在子进程内直接落盘；TwinCAT 数据由 Session 主 writer 写入 CSV。
3. 录制结束后，使用 `verify_alignment.py` 估计 PLC-PC 时钟漂移模型。
4. 使用 `unify_alignment.py` 生成以机器人位姿为锚点的统一对齐表。

## 5. 已验证的关键结论

### 5.1 独立进程采集稳定

- 每个相机运行在独立 OS 进程，避免 Windows DirectShow 多线程冲突。
- 单个相机的写盘瓶颈不会影响其他源。
- 已通过 5 分钟连续测试，无进程崩溃、无严重丢帧。

### 5.2 TwinCAT 多连接有效但伴随重复数据

| 连接数 | 实测频率 | 备注 |
|---|---|---|
| 单连接（全 8 类符号） | ~320–340 Hz/臂 | RTT ~3.2 ms |
| 双连接 | ~650 Hz（总样本） | 出现大量重复 CycleCount |

**结论**：Python/ADS 端优化已到位。继续提升到 1 kHz 需检查 PLC 任务周期、ADS 路由，或减少读取符号数量。

### 5.3 跨模态时间对齐精度（2026-08-03 样例）

**方法**：以 PLC 时间轴为统一参考，将视频帧 PC 时间戳通过线性模型 `timestamp_ns_plc = k * timestamp_ns_pc + b` 映射到 PLC 时间，再寻找最近邻位姿。

**样例 `sessions/test_20260803_104724` 结果**：

| 相机 | 有效帧数 | 平均对齐误差 | 标准差 | 最大误差 |
|---|---|---|---|---|
| camera_arm_1 | 1,717 | **0.83 ms** | 0.52 ms | 2.91 ms |
| camera_arm_2 | 2,379 | **0.84 ms** | 0.51 ms | 2.34 ms |
| camera_arm_3 | 1,666 | **0.84 ms** | 0.51 ms | 2.11 ms |

**结论**：对齐精度在 1 ms 以内，方案可用。

### 5.4 统一对齐表质量

使用 `unify_alignment.py` 以机器人位姿为锚点生成统一 CSV：

- 总位姿行数：25,328
- 三相机均有效行数：23,364（**92.2%**）
- 统一对齐后，三路相机图像间的时间差：arm_1 ≈ 11.4 ms，arm_2 ≈ 8.3 ms，arm_3 ≈ 11.4 ms

## 6. 多模态时间对齐策略分析

### 6.1 问题背景

采集系统同时记录：
- **视觉数据**：三路 USB 相机，帧率 22–30 fps（离散帧，不可插值）。
- **运动学数据**：TwinCAT ADS 位姿，实际约 312 Hz（连续信号，可插值）。

核心矛盾：**图像是离散采样的，无法在不引入伪影的情况下插值出中间帧；而机械臂位姿是连续信号，可以线性插值或 SLERP 插值。** 因此严格意义上的“零误差同步”不可能实现，只能在不同策略之间做取舍。

### 6.2 策略一：以机器人为基准，取三相机最近帧

**做法**：对每个机器人位姿样本，分别在三路相机中找时间最近的帧，把时间差作为误差列保留。当前 `unify_alignment.py` 采用此策略。

**优点**：
- 保留最高频率的机器人动作信息（不丢失 312 Hz 动作细节）。
- 实现简单，每个机器人时刻都有视觉观测。
- 便于训练“动作 → 下一时刻动作/图像”的模型。

**缺点**：
- 三张图像之间存在时间差（arm_1/arm_3 约 ±11 ms，arm_2 约 ±8 ms）。
- 快速运动场景下，三张图可能拍到机械臂不同空间位置。

**当前实测结果**（`test_20260803_104724`）：

| 相机 | 均值 | 标准差 | 最大值 | 中位数 | 95% 分位 |
|------|------|--------|--------|--------|----------|
| camera_arm_1 | 11.38 ms | 6.78 ms | 24.87 ms | 11.09 ms | 22.57 ms |
| camera_arm_2 | 8.35 ms | 4.82 ms | 18.47 ms | 8.49 ms | 15.86 ms |
| camera_arm_3 | 11.40 ms | 6.77 ms | 24.52 ms | 11.13 ms | 22.55 ms |

**改进方法**：设置误差阈值过滤，只保留三相机误差均小于阈值的样本：

```python
MAX_ERRORS = {
    'camera_arm_1': 10.0,  # ms
    'camera_arm_2': 8.0,
    'camera_arm_3': 10.0,
}
valid = df[
    (df['camera_arm_1_alignment_error_ms'] < MAX_ERRORS['camera_arm_1']) &
    (df['camera_arm_2_alignment_error_ms'] < MAX_ERRORS['camera_arm_2']) &
    (df['camera_arm_3_alignment_error_ms'] < MAX_ERRORS['camera_arm_3'])
]
```

### 6.3 策略二：以某一相机为基准，插值机器人位姿

**做法**：选择 arm_2（30 fps，最稳定）作为主时间轴。对每个 arm_2 帧时刻：
- 找 arm_1、arm_3 的最近帧；
- 用线性插值（位置）+ SLERP（姿态四元数）得到该精确时刻的机器人位姿。

**优点**：
- 三张图像真正“接近同一时刻”。
- 机器人位姿误差可以做得非常小（< 1 ms）。

**缺点**：
- 数据频率被限制在主相机的帧率（如 30 Hz）。
- 需要位姿插值，要求机器人运动平滑；若存在抖动或急停，插值可能失真。

**适用场景**：三维重建、多视角一致性检测等更关心“某一时刻三视角图像 + 该时刻位姿”的任务。

### 6.4 策略三：多时间尺度对齐

**做法**：
- **高频分支**：机器人位姿保持 312 Hz，用于精细动作建模。
- **低频同步分支**：每隔 33 ms（对应 arm_2 帧率）创建一个“同步帧”，包含三相机最近帧 + 插值位姿。

**优点**：既保留高频机器人信息，又有严格同步的多视图样本。

**缺点**：数据存储和读取逻辑更复杂，需要维护两个时间索引。

### 6.5 当前推荐方案

推荐 **策略一 + 严格误差过滤**，原因：

1. 机器人位姿频率远高于相机，以机器人为基准不会丢失动作细节。
2. 8–11 ms 的图像时间差远小于单帧周期（33–44 ms），对大多数视觉-语言-动作模型影响有限。
3. 实现和维护成本低，便于快速迭代。

如果后续实验发现三图不同步严重影响模型性能，再引入 **策略二** 生成一个 30 Hz 的严格同步子集进行对比实验。

## 8. 与计算机学院老师讨论的关键问题

以下问题希望在与老师的交流中得到指导：

### 8.1 时间对齐策略选择

- **问题**：策略一（机器人锚点 + 最近帧，保留 312 Hz，三图有 8–11 ms 差）vs 策略二（相机锚点 + 位姿插值，严格同步但降至 30 Hz）。
- **背景**：VLGP 模型通常需要高频动作序列，但多视图一致性也很重要。
- **希望得到的指导**：从机器人学习/多模态学习的角度，哪种时间对齐方式更合理？是否需要同时维护两个分支的数据集？

### 8.2 机器人位姿频率不足

- **问题**：TwinCAT 目标 1 kHz，但 Python/ADS 端实测约 320–340 Hz/臂（已读取全部 8 类符号）。
- **已尝试**：独立 ADS 连接、多连接并行、RTT 校正、读取 CycleCount、四臂同时输出等。
- **希望得到的指导**：
  - 1 kHz 是否为硬性需求？
  - 如果是，瓶颈更可能在 PLC 任务周期、ADS 路由，还是 Python 读取策略？
  - 是否有建议的 PLC 端或 PC 端优化方向？

### 8.3 相机帧率不一致

- **问题**：arm_1 / arm_3 物理上限 22.5 fps，arm_2 可达 30–60 fps。
- **希望得到的指导**：
  - 这种帧率差异是否会影响模型训练？
  - 是否需要统一降采样到 22.5 fps，还是保留 arm_2 的更高帧率？
  - 是否需要硬件升级（如替换为 30 fps 相机）？

## 11. 数据自主标注的讨论与规划

### 11.1 自主标注是否必要？

采集框架本身解决的是「如何稳定、精确地记录多模态数据」问题。但 VLGP（Vision-Language-Guided Procedure）研究需要的不只是原始信号，而是**可训练的（视觉，语言，动作）三元组**。因此：

- 如果目标是「采集与对齐框架」论文：自主标注可作为 downstream application 或 future work，不必作为核心贡献。
- 如果目标是「构建 VLGP 手术机器人数据集」或「端到端 VLGP 系统」：自主标注是必需的，甚至是核心研究问题之一。

### 11.2 最可行的自动标注方向

基于当前已采集的数据，建议按以下优先级推进：

#### 阶段 1：基于运动学状态的自动标注（已具备数据）

利用 TwinCAT 返回的位姿、关节角、器械类型，自动提取：

| 标注类型 | 计算方法 | 用途 |
|---|---|---|
| 器械运动事件 | 末端速度/加速度峰值 | 「插入」「回撤」「夹取」等 |
| 运动阶段分割 | 位姿轨迹聚类 / 变点检测 | 自动划分手术阶段 |
| 静止/运动区间 | 位姿变化阈值 | 标注 idle / active 片段 |
| 工具切换事件 | `instrument_types` 变化 | 工具使用序列 |
| 工作空间区域 | 3D 末端位置聚类 | 视野左/右侧操作 |

#### 阶段 2：基于视觉的自动标注

| 标注类型 | 方法 | 用途 |
|---|---|---|
| 器械检测/分割 | 预训练手术器械检测模型 | bounding box / mask |
| 关键帧提取 | 根据运动学事件定位视频帧 | 动作起止帧 |
| 异常检测 | 视觉与运动学不一致 | 数据清洗 |

#### 阶段 3：语言标注生成（VLGP 核心）

| 方向 | 示例 | 难度 |
|---|---|---|
| 模板化语言生成 | 「使用抓钳进行快速移动」 | 低 |
| 手术步骤描述生成 | 「将抓钳移动到左侧，夹持组织」 | 高 |
| 动作-语言对齐 | 把自然语言指令映射到视频片段和位姿序列 | 中高 |

### 11.3 风险与边界

- **临床有效性**：自动标注需经医生或机器人工程师小规模校验，低置信度样本送人工确认。
- **Scope 控制**：建议先聚焦「基于运动学的阶段分割」一个点，避免同时铺开视觉分割、大语言模型、端到端训练。
- **隐私与伦理**：手术数据需 IRB/伦理审批、脱敏与访问控制。

### 11.4 与老师讨论时可提出的问题

1. 自主标注应作为独立研究方向，还是采集系统的 downstream application？
2. 模板化生成 vs 视觉-语言大模型生成，哪个更适合当前阶段？
3. 如何在没有大量人工标注的情况下评估自动标注质量？
4. 手术机器人自动标注更适合投 ICRA、MICCAI 还是 CVPR/ACL？

## 12. 视频片段与动作序列的对齐

### 12.1 问题重述

如果无法做到「每一帧图像 ↔ 每一个机器人状态」的精确一一对齐，是否可以改为：

> 传入一段视频片段（连续 N 帧图像）和对应时间窗口内的机器人动作状态序列，对这两个序列进行对齐？

### 12.2 结论：可以，且在很多场景下更合理

**答案是肯定的。** 这种「序列对序列」的对齐不仅可行，而且在 VLGP 研究中往往比逐帧对齐更自然：

- 人类的手术操作指令通常是**时间段级别**的（例如「夹持组织 3 秒」），而不是单帧级别的。
- 视频帧率和机器人状态频率差异巨大（22–30 fps vs 312 Hz），强行逐帧对齐会造成大量插值或丢弃。
- 视频片段包含时序上下文，对动作识别更有帮助。

### 12.3 技术路线

#### 12.3.1 传统方法

| 方法 | 核心思想 | 适用场景 |
|---|---|---|
| **Dynamic Time Warping (DTW)** | 寻找两条序列间的最优非线性时间弯曲 | 视频特征序列与状态序列长度不同、采样率不同 |
| **Canonical Correlation Analysis (CCA)** | 学习两个模态特征子空间的线性映射 | 需要训练数据但无显式时间标签 |
| **Cross-Correlation** | 计算两个时序信号的互相关峰值 | 信号有明显同步事件 |
| **HMM / CTC** | 用隐状态建模动作阶段，进行软对齐 | 有阶段标签或动作类别 |

#### 12.3.2 深度学习方法

| 方法 | 核心思想 | 代表工作 |
|---|---|---|
| **Temporal Cycle Consistency (TCC)** | 学习视频帧之间的循环一致性表征 | CVPR 2019 |
| **Time-Contrastive Networks (TCN)** | 同一时刻不同视角为正样本，不同时刻为负样本 | ICRA 2018 |
| **LAV (Local Alignment Verbs)** | 视频片段与自然语言指令的局部时间对齐 | CVPR |
| **Contrastive Learning** | 拉近同步的视频片段和动作序列，推远不同步的 | 通用框架 |
| **Transformer Cross-Attention** | 用交叉注意力学习视频帧与状态序列的软对齐 | 当前主流 |

### 12.4 在本项目中的实现思路

结合现有数据，可按以下步骤尝试：

1. **特征提取**
   - 视频片段：用预训练 CNN（ResNet、Video Swin、TimeSformer）提取帧级或片段级特征。
   - 动作序列：用位姿速度、关节角变化、器械状态等构造状态特征向量。

2. **时序建模**
   - 对视频特征序列用 1D-CNN 或 Transformer encoder 建模局部时序。
   - 对动作状态序列用相同结构编码。

3. **对齐损失**
   - **对比损失**：同一操作片段的视频特征与动作特征拉近，不同操作推远。
   - **DTW 损失**：最小化两个特征序列的最优对齐距离。
   - **阶段分类损失**：如果已知阶段标签，用交叉熵约束对齐。

4. **输出形式**
   - 软对齐矩阵：视频第 i 帧与动作第 j 步的对应概率。
   - 粗粒度对应：视频片段 ↔ 动作子序列。
   - 语言描述生成：基于对齐结果生成「在这段时间内，机器人执行了 XX 动作」。

### 12.5 优势与挑战

**优势**：
- 不要求精确的帧级时间戳对应。
- 自然处理不同采样率。
- 更符合 VLGP 中语言指令的时间粒度。
- 可利用大量未配对的多模态数据进行自监督预训练。

**挑战**：
- **相似动作歧义**：例如反复「夹持-松开」容易造成对齐混淆。
- **时间粒度选择**：片段太短则失去上下文，太长则对齐模糊。
- **缺乏 ground truth**：评估对齐质量需要人工标注或设计代理指标。
- **计算成本**：视频特征提取和序列比对计算量较大。

### 12.6 与当前采集框架的结合

当前系统已经为这种片段级对齐提供了良好基础：

- `unify_alignment.py` 已经给出了「某段机器人位姿 ↔ 某段视频帧」的粗对应。
- `analyze_session.py` 可以输出时间覆盖率和同步质量，帮助选择高质量片段。
- 下一步可以基于 `unified_alignment_valid.csv` 中的有效窗口，训练一个片段级对齐模型。

### 12.7 建议的研究问题

如果要把这个方向作为论文贡献，可以定位成：

> *"Weakly-supervised temporal alignment between video clips and robot state sequences for surgical procedure understanding"*

或

> *"Learning coarse-to-fine cross-modal alignment for vision-language-guided surgical robots"*

## 13. SRT-H 数据格式与我们的数据构建方案

### 13.1 SRT-H 数据格式总结

根据 SRT-H 论文源码分析，其训练数据格式如下：

**视觉输入**：
- 立体内窥镜左目：960×540，训练时 resize 到 224×224
- 左/右手腕相机：640×480，训练时 resize 到 224×224
- 统一 30 fps
- HL policy：当前帧 + 过去 4 帧，每帧间隔 1 秒
- LL policy：当前时刻三路图像

**机器人动作**：
- 双臂 PSM1 + PSM2
- 位置 `position.x/y/z` + 四元数 `orientation.x/y/z/w`
- 动作表示：hybrid-relative（平移相对内窥镜尖端，旋转相对末端执行器）
- 动作空间：20 维 = 每臂 3（平移）+ 6（6D 旋转）+ 1（夹爪）
- Action chunking：k=60（30 fps × 2 秒）

**语言标注**：
- Task instruction：如 `"grabbing gallbladder"`, `"clipping first clip left tube"`
- Corrective instruction：如 `"move left arm to the right"`
- Correction flag：是否处于 recovery 模式

**数据规模**：
- 约 16,000 条 demonstrations
- 34 个 ex-vivo 猪胆囊
- 17 个任务（抓胆囊 + 12 个 clip + 4 个 cut）

### 13.2 我们当前系统与 SRT-H 的映射

| 项目 | SRT-H | 我们当前系统 |
|---|---|---|
| 相机配置 | 内窥镜 + 2 手腕相机 | arm_2 内窥镜 + arm_1/arm_3 手腕相机 |
| 臂数 | 2 条手术臂 | 4 条臂（arm_1/arm_3 常用手，arm_2 内窥镜，arm_4 非常用手） |
| 帧率 | 统一 30 fps | arm_2 30 fps，arm_1/arm_3 22.5 fps（后续升级） |
| 动作表示 | hybrid-relative delta | 当前为绝对位姿，需转换 |
| 语言标注 | 任务标注 + 自动生成纠正指令 | 当前无，需构建 |

### 13.3 我们的数据构建方案

#### 13.3.1 动作空间：统一 4 臂 + activation mask

## 14. 模仿学习中的手抖与错误恢复数据问题

### 14.1 医生手抖会影响模型学习吗？

**结论：会，但影响程度取决于手抖的性质和数据量。**

#### 14.1.1 小手抖（高频低幅）

- **影响较小**：神经网络具有平均效应，大量 demonstration 中的随机手抖会相互抵消，模型倾向于学习平滑的平均轨迹。
- **甚至有好处**：适当的手抖相当于数据增强，可以提升模型的鲁棒性。

#### 14.1.2 显著抖动 / 修正性微动

- **可能产生负面影响**：
  - 模型可能学会不必要的抖动轨迹
  - 在接近目标点时产生振荡
  - 夹爪开合时机被手抖干扰
- **典型表现**：
  - 预测轨迹 jerk 较大
  - 在目标位置附近反复修正
  - 动作 chunk 中出现高频波动

#### 14.1.3 缓解方法

| 方法 | 做法 | 效果 |
|---|---|---|
| **动作平滑（Low-pass filter）** | 对位姿序列做 Savitzky-Golay 或高斯平滑 | 去除高频手抖 |
| **Delta action 正则化** | 在 loss 中加入动作变化率惩罚 | 鼓励平滑轨迹 |
| **数据增强** | 在训练时添加可控噪声 | 提升泛化性 |
| **增加数据量** | 更多医生/更多 demonstration | 随机手抖自然平均 |
| **Quality filtering** | 用 jerk/平滑度指标过滤低质量 demo | 剔除严重抖动样本 |
| **Diffusion policy / VQ-VAE** | 生成式模型天然学习分布均值 | 自动平滑 |

**具体建议**：
- 在数据预处理阶段对绝对位姿做轻微平滑（窗口 3–5 帧）
- 训练时在 L1 loss 基础上加入动作加速度惩罚
- 对明显异常的 demonstration（如 jerk 超过阈值 3 倍）进行人工复核

### 14.2 错误状态恢复数据需要收集多少？

**结论：不是越多越好，关键是多样性和比例。**

#### 14.2.1 参考比例

| 来源 | 最优数据 | 恢复数据 | 恢复数据比例 |
|---|---|---|---|
| SRT-H | 13,189 条 | 5,167 条 | ~28% |
| 一般模仿学习 | — | — | 10%–30% |
| 简单任务初期 | 50–100 条 | 10–30 条 | ~15%–25% |

#### 14.2.2 比数量更重要的是多样性

对于每个任务，应覆盖主要失败模式：

**触针任务**：
- 针偏左时的恢复
- 针偏右时的恢复
- 针偏高/偏低时的恢复
- 夹爪过早闭合的恢复

**抓针任务**：
- 夹取位置偏斜的恢复
- 未夹住针的恢复
- 夹住但滑脱的恢复

**缝合任务**：
- 针刺入角度错误的恢复
- 线缠绕的恢复
- 打结松动的恢复

#### 14.2.3 更高效的收集方式：DAgger

单纯离线收集 recovery demonstrations 效率不高，更推荐 **DAgger-style** 在线收集：

1. 先用最优数据训练一个 base policy
2. 部署 policy，观察其失败模式
3. 在失败状态下，由医生给出纠正指令
4. 记录（失败状态图像，纠正指令，纠正动作）三元组
5. 用新数据 fine-tune policy
6. 重复 2–5 步

**优点**：
- 只收集 policy 实际会犯的错误，数据利用率高
- 和 SRT-H 的 HL DAgger 思路一致
- 通常 2–3 轮迭代就能看到明显改善

#### 14.2.4 针对你们三个任务的建议

| 任务 | 最优数据 | 恢复数据 | 备注 |
|---|---|---|---|
| 触针 | 50–80 条 | 每条失败模式 5–10 条 | 覆盖 4–6 种偏移方向 |
| 抓针 | 80–120 条 | 每条失败模式 8–12 条 | 重点覆盖滑脱和偏斜 |
| 缝合 | 150–300 条 | 占总数据 20–30% | 失败模式更复杂，需要更多 |

#### 14.2.5 恢复数据的标注要点

每条 recovery demonstration 需要记录：
- **进入失败状态前的 3 秒上下文**（SRT-H 的做法）
- **失败状态的具体类型**（用于分析失败分布）
- **纠正指令**（自然语言）
- **纠正后的动作序列**
- **最终是否恢复成功**

### 14.3 给老师讨论的要点

1. 手抖是否应该被显式过滤？还是让模型自己学习平滑化？
2. 恢复数据的最佳比例是多少？是否需要根据任务难度动态调整？
3. 是否应采用 DAgger 方式在线收集恢复数据，而不是离线录制？
4. 如何定义和分类手术任务的失败模式？
5. 手抖是否可以作为一种数据增强，提升模型对传感器噪声的鲁棒性？

## 15. DAgger 具体操作流程

### 15.1 核心思想

DAgger（Dataset Aggregation）在本项目中的核心思想：

> **先训练一个 base policy，让它在实际任务中犯错；然后由医生在错误状态下给出纠正，把这些（错误状态 + 纠正指令 + 纠正动作）加入数据集，重新训练 policy。**

SRT-H 的论文里把这叫 **HL DAgger**，因为他们主要纠正的是 **High-level policy 的语言输出**，而不是每一帧的低层动作。

### 15.2 整体流程

```text
第 0 轮：收集最优演示数据 D_base
    ↓
训练 base policy π_0（HL + LL）
    ↓
for iteration = 1, 2, 3, ...:
    部署 π_{i-1} 执行任务
    ↓
    policy 进入失败/次优状态
    ↓
    医生给出纠正（语言 + 动作）
    ↓
    记录 D_corr_i
    ↓
    D_i = D_base ∪ D_corr_1 ∪ ... ∪ D_corr_i
    ↓
    在 D_i 上 fine-tune policy 得到 π_i
```

### 15.3 三种纠正方式

#### 15.3.1 方式 A：纯语言纠正（SRT-H 方式）

**流程**：
1. Policy 自主运行
2. 医生观察到失败趋势或失败状态
3. 医生说出纠正指令，如「左臂往右一点」「张开夹爪」
4. 语音转文本后送入 LL policy，替代 HL policy 的指令
5. LL policy 根据纠正指令生成动作
6. 状态恢复后切回 HL policy 自主控制

**优点**：不需要手动操作机器人，数据标注自动（语音转文本）。
**缺点**：需要语音识别系统，词汇表受限。

#### 15.3.2 方式 B：医生 Teleoperation 纠正

**流程**：
1. Policy 运行
2. 医生按下「接管」按钮
3. 医生用手柄/主手 teleoperate 机器人完成恢复
4. 松开接管按钮，policy 恢复自主
5. 事后为恢复段标注纠正语言

**优点**：纠正动作更自然准确，词汇表不限。
**缺点**：医生操作负担重，事后需补充语言标注。

#### 15.3.3 方式 C：GUI 按钮纠正（推荐初期使用）

**流程**：
1. 准备 GUI，显示常用纠正指令按钮：
   - 方向类：「左臂往右」「右臂往左」「左臂上」等
   - 夹爪类：「张开左夹爪」「闭合左夹爪」等
   - 任务类：「重新定位针」「拉紧线」等
2. Policy 运行
3. 医生点击按钮
4. 按钮对应指令送入 LL policy
5. 执行 3–5 秒后自动切回 HL policy

**优点**：无需语音识别，语言标签直接由按钮决定，最容易快速实现。
**缺点**：词汇表受限，不如自然语言灵活。

### 15.4 D_corr 样本格式

```python
{
    "observation_history": {
        "endoscope": [90, 224, 224, 3],      # 失败前 3 秒 @ 30 Hz
        "wrist_left": [90, 224, 224, 3],
        "wrist_right": [90, 224, 224, 3]
    },
    "original_hl_output": {
        "task_instruction": "insert needle",
        "correction_flag": False,
        "corrective_instruction": ""
    },
    "corrective_language": "move left arm to the right",
    "corrective_actions": [90, 40],           # 3 秒 @ 30 Hz，40 维 4 臂动作
    "arm_active_mask": [90, 4],
    "task_name": "suture insertion",
    "failure_mode": "needle_deviated_left",   # 失败模式分类
    "recovery_success": True,
    "operator_id": "doctor_001",
    "timestamp": "..."
}
```

### 15.5 Fine-tune 策略

#### HL Policy Fine-tune

```python
D_merged = D_base ∪ D_corr

train_hl_policy(
    dataset=D_merged,
    learning_rate=1e-6,  # 比 base 训练更小
    epochs=300,
    loss_weights={
        "task_loss": 1.0,
        "correction_flag_loss": 2.0,
        "corrective_instruction_loss": 2.0
    }
)
```

**技巧**：
- 60% 训练样本从 recovery demonstrations 开始
- 加重 correction_flag 和 corrective_instruction 的 loss 权重
- 使用较小学习率，避免遗忘 base 能力

#### LL Policy Fine-tune

```python
train_ll_policy(
    dataset=D_merged
    # 同时包含 task instructions 和 corrective instructions
)
```

### 15.6 迭代计划

| 轮次 | 目标 |
|---|---|
| 第 1 轮 | 覆盖最常见的 3–5 种失败 |
| 第 2 轮 | 覆盖第 1 轮 policy 新暴露的失败 |
| 第 3 轮 | 处理长尾失败模式 |
| 第 4 轮+ | 边际收益递减，视情况停止 |

**停止条件**：
- 成功率达到可接受水平
- 新增纠正数据不再显著改善性能
- 失败模式已充分覆盖

### 15.8 最小可行版本（第一周验证）

1. **只做一个任务**：抓针
2. **收集 5–10 条恢复数据**
3. **使用 GUI 按钮纠正**：6–8 个方向 + 开闭夹爪
4. **只 fine-tune HL policy**
5. **评估指标**：policy 在相同失败状态下能否自动恢复

### 15.9 关键注意事项

- **安全第一**：机器人必须在安全速度限制下运行，医生可随时急停
- **失败模式多样化**：不要只收集同一种失败的纠正
- **纠正数据比例**：建议控制在 10%–30%，过多会让模型「预期失败」
- **记录医生 ID**：不同医生纠正风格不同，便于分析
- **语言标准化**：尽量使用规范化的纠正指令文本
