### 3.1 新相机 cam1 帧率特性详测（2026-08-05/06）

对新接入相机（当前 index 1，640×480 MJPG）做了系统性测试：18 组「曝光 × FPS × 后端」扫描、dshow 离散模式映射（11 档）、60 秒软件抽取验证、MSMF 高优先级专项测试。

**各方案对比**：

| 方案 | 实际 FPS | 帧间隔 std | 最大间隔 | 结论 |
|---|---|---|---|---|
| dshow 原生（不设 FPS） | 64 或 120（**每次启动不确定**） | 2.2–5.9 ms | — | 不能当固定帧率用；“64 fps 怪数值”的来源 |
| dshow + 设置任意 FPS | **31.5**（所有档位都映射到同一模式） | **~1.0 ms** | ~35 ms | 最均匀，但数值不是 30 |
| MSMF + 任意 FPS（含 60） | ~30.1（封顶，**不可能 60**） | ~6.5 ms | ~66 ms | ~1% 帧规律跳拍（~64 ms 间隔），高精度定时器/高优先级无法改善 |
| **dshow 原生 + 软件网格抽帧到 30** | **30.01** | 4.0 ms | 48.5 ms | 唯一精确 30 的方案 |
| **dshow 原生 + 软件网格抽帧到 60** | **60.01** | 3.3 ms | 32.5 ms | 唯一精确 60 的方案 |

**其他发现**：

- 采集 worker 固定曝光（`usb_camera_worker.py` 的 `AUTO_EXPOSURE=0.25, EXPOSURE=-6`）能解除自动曝光对帧率的限制，session `test_20260806_203701` 中相机实测跑到 ~64 fps 且 std 仅 2.18 ms。
- MSMF 已验证支持多相机同时采集（cam0+cam1 同采均 ~30 fps，无读取失败），可作为 dshow 多相机冲突时的备选，但需接受 ~1% 的 ~64 ms 跳帧与 30 fps 封顶。
- `fps: null` 时 worker 不再触碰 `CAP_PROP_FPS`（已修复）；写入配置的 `fps` 值会被 dshow 映射到 31.5 fps 模式，名义帧率与实际不符。

**推荐用法**：

- 要精确 30.00 / 60.00 fps：dshow 原生流 + 软件网格抽帧（建议在 `usb_camera_worker.py` 的 capture loop 实现 `target_fps` 抽帧器，保留真实 PC 时间戳）。
- 只要接近 30 且最均匀：dshow + `fps: 30`（实际 31.5 fps，std ~1 ms）。
- 多相机冲突备选：MSMF（30.1 fps，接受周期性跳帧）。

**重要修正（2026-08-07）**：用户通过 `preview_single_camera.bat` 发现该相机可稳定 60 fps，复核后确认**属实**。关键在于 **OpenCV 属性设置顺序**：preview 脚本的顺序是 `BUFFERSIZE → 宽 → 高 → FPS → FOURCC`（FPS 在 FOURCC **之前**），此顺序下：

| 配置（dshow，预览顺序） | 实际 FPS | std | max |
|---|---|---|---|
| 1280×720, fps=30 或 60 | **60.1** | 3.2 ms | 33 ms |
| 640×480, fps=30 或 60 | 64.1 | 2.2 ms | 19 ms |

而之前扫描中 `FOURCC → FPS` 的顺序会让驱动选到低速模式（1280×720 仅 9.5 fps）。采集 worker 的属性顺序恰好与 preview 一致（FPS 在 FOURCC 前），因此**正式采集也能跑到 60 fps**：`test_cam1_60fps_worker` 端到端验证 1280×720 JPG = **60.11 fps**，std 3.35 ms，max 34.6 ms。`default.yaml` 中 camera_arm_1 已更新为 1280×720 @ 60 fps（dshow, MJPG, jpg）。

注意：用户观察到的“60 fps”实际是 **dshow** 后端（preview 批处理默认 dshow）；MSMF 仍封顶 30.1 fps。

**target_fps 软件抽帧器与 PNG 写盘（2026-08-07）**：

- `usb_camera_worker.py` 新增 `--target-fps`：相机跑原生高速流，capture loop 按虚拟时间网格保留真实帧（真实 PC 时间戳），输出精确帧率。`fps`（驱动模式选择）与 `target_fps`（输出速率）独立，可同时设置。
- PNG 编码吞吐实测（本机）：720p level 1 = 39.3 ms/帧（单线程仅 25.5 fps，**跟不上 30**）；level 0 = 19.9 ms/帧（50 fps，但 2.8 MB/帧、79 MB/s 逼近磁盘极限）；480p level 1 = 11.4 ms/帧（87.8 fps，足够）。
- 新增 `--writer-threads`（多 writer 线程共享队列 + 元数据写锁）：720p PNG level 1 双线程端到端验证 **30.05 fps**（cam1 720p 原生 60 → 抽帧 30，std 5.0 ms）。PNG 任意压缩级别均无损，level 只影响文件大小与编码耗时。
- 多 writer 时 metadata.csv 行可能乱序，三个对齐工具（`align_camera_anchor.py` / `unify_alignment.py` / `verify_alignment.py`）已改为读取后按 `timestamp_ns` 排序。
- `default.yaml` 当前为：arm_2 720p@30（PNG、双 writer）、arm_1 480p@30（PNG）、arm_3 480p@30（PNG，未接入故 disabled）；三者均 `fps: 60`（驱动高速模式）+ `target_fps: 30`（精确输出）。
- 排查过程中确认：**当前 index 0 不是内窥镜**（是一个房景摄像头，原生仅 ~29.7 fps）；内窥镜重新接入后需重新跑 `camera_assignment_setup` 确认索引。
- `run_acquisition.py` 现在也支持配置项 `enabled: false` 跳过该源（此前只有 `manual_acquisition.py` 支持）。

### 6.2 策略一：以机器人为基准，取三相机最近帧

**做法**：对每个机器人位姿样本，分别在三路相机中找时间最近的帧，把时间差作为误差列保留。当前 `unify_alignment.py` 采用此策略。

**优点**：
- 保留最高频率的机器人动作信息（不丢失 312 Hz 动作细节）。
- 实现简单，每个机器人时刻都有视觉观测。
- 便于训练“动作 → 下一时刻动作/图像”的模型。

**缺点**：
- 三张图像之间存在时间差（arm_1/arm_3 约 ±11 ms，arm_2 约 ±8 ms）。
- 快速运动场景下，三张图可能拍到机械臂不同空间位置。

**当前实测结果**（`test_20260803_104724`）：

| 相机 | 均值 | 标准差 | 最大值 | 中位数 | 95% 分位 |
|------|------|--------|--------|--------|----------|
| camera_arm_1 | 11.38 ms | 6.78 ms | 24.87 ms | 11.09 ms | 22.57 ms |
| camera_arm_2 | 8.35 ms | 4.82 ms | 18.47 ms | 8.49 ms | 15.86 ms |
| camera_arm_3 | 11.40 ms | 6.77 ms | 24.52 ms | 11.13 ms | 22.55 ms |

**改进方法**：设置误差阈值过滤，只保留三相机误差均小于阈值的样本：

```python
MAX_ERRORS = {
    'camera_arm_1': 10.0,  # ms
    'camera_arm_2': 8.0,
    'camera_arm_3': 10.0,
}
valid = df[
    (df['camera_arm_1_alignment_error_ms'] < MAX_ERRORS['camera_arm_1']) &
    (df['camera_arm_2_alignment_error_ms'] < MAX_ERRORS['camera_arm_2']) &
    (df['camera_arm_3_alignment_error_ms'] < MAX_ERRORS['camera_arm_3'])
]
```

### 6.4 策略三：多时间尺度对齐

**做法**：
- **高频分支**：机器人位姿保持 312 Hz，用于精细动作建模。
- **低频同步分支**：每隔 33 ms（对应 arm_2 帧率）创建一个“同步帧”，包含三相机最近帧 + 插值位姿。

**缺点**：数据存储和读取逻辑更复杂，需要维护两个时间索引。

## 12. 视频片段与动作序列的对齐

### 12.1 问题重述

如果无法做到「每一帧图像 ↔ 每一个机器人状态」的精确一一对齐，是否可以改为：

> 传入一段视频片段（连续 N 帧图像）和对应时间窗口内的机器人动作状态序列，对这两个序列进行对齐？

### 12.2 结论：可以，且在很多场景下更合理

**答案是肯定的。** 这种「序列对序列」的对齐不仅可行，而且在 VLGP 研究中往往比逐帧对齐更自然：

- 人类的手术操作指令通常是**时间段级别**的（例如「夹持组织 3 秒」），而不是单帧级别的。
- 视频帧率和机器人状态频率差异巨大（22–30 fps vs 312 Hz），强行逐帧对齐会造成大量插值或丢弃。
- 视频片段包含时序上下文，对动作识别更有帮助。

### 12.3 技术路线

#### 12.3.1 传统方法

| 方法 | 核心思想 | 适用场景 |
|---|---|---|
| **Dynamic Time Warping (DTW)** | 寻找两条序列间的最优非线性时间弯曲 | 视频特征序列与状态序列长度不同、采样率不同 |
| **Canonical Correlation Analysis (CCA)** | 学习两个模态特征子空间的线性映射 | 需要训练数据但无显式时间标签 |
| **Cross-Correlation** | 计算两个时序信号的互相关峰值 | 信号有明显同步事件 |
| **HMM / CTC** | 用隐状态建模动作阶段，进行软对齐 | 有阶段标签或动作类别 |

#### 12.3.2 深度学习方法

| 方法 | 核心思想 | 代表工作 |
|---|---|---|
| **Temporal Cycle Consistency (TCC)** | 学习视频帧之间的循环一致性表征 | CVPR 2019 |
| **Time-Contrastive Networks (TCN)** | 同一时刻不同视角为正样本，不同时刻为负样本 | ICRA 2018 |
| **LAV (Local Alignment Verbs)** | 视频片段与自然语言指令的局部时间对齐 | CVPR |
| **Contrastive Learning** | 拉近同步的视频片段和动作序列，推远不同步的 | 通用框架 |
| **Transformer Cross-Attention** | 用交叉注意力学习视频帧与状态序列的软对齐 | 当前主流 |

### 12.4 在本项目中的实现思路

结合现有数据，可按以下步骤尝试：

1. **特征提取**
   - 视频片段：用预训练 CNN（ResNet、Video Swin、TimeSformer）提取帧级或片段级特征。
   - 动作序列：用位姿速度、关节角变化、器械状态等构造状态特征向量。

2. **时序建模**
   - 对视频特征序列用 1D-CNN 或 Transformer encoder 建模局部时序。
   - 对动作状态序列用相同结构编码。

3. **对齐损失**
   - **对比损失**：同一操作片段的视频特征与动作特征拉近，不同操作推远。
   - **DTW 损失**：最小化两个特征序列的最优对齐距离。
   - **阶段分类损失**：如果已知阶段标签，用交叉熵约束对齐。

4. **输出形式**
   - 软对齐矩阵：视频第 i 帧与动作第 j 步的对应概率。
   - 粗粒度对应：视频片段 ↔ 动作子序列。
   - 语言描述生成：基于对齐结果生成「在这段时间内，机器人执行了 XX 动作」。

### 12.5 优势与挑战

**优势**：
- 不要求精确的帧级时间戳对应。
- 自然处理不同采样率。
- 更符合 VLGP 中语言指令的时间粒度。
- 可利用大量未配对的多模态数据进行自监督预训练。

**挑战**：
- **相似动作歧义**：例如反复「夹持-松开」容易造成对齐混淆。
- **时间粒度选择**：片段太短则失去上下文，太长则对齐模糊。
- **缺乏 ground truth**：评估对齐质量需要人工标注或设计代理指标。
- **计算成本**：视频特征提取和序列比对计算量较大。

### 12.6 与当前采集框架的结合

当前系统已经为这种片段级对齐提供了良好基础：

- `unify_alignment.py` 已经给出了「某段机器人位姿 ↔ 某段视频帧」的粗对应。
- `analyze_session.py` 可以输出时间覆盖率和同步质量，帮助选择高质量片段。
- 下一步可以基于 `unified_alignment_valid.csv` 中的有效窗口，训练一个片段级对齐模型。

或

## 16. PTP 时间同步调研（2026-08-05）

**背景**：当前跨模态对齐采用「PC 软时间戳 + 事后线性漂移校准」，误差 ~1 ms，对 30 Hz 数据足够。若未来需要**精确曝光时刻**（三维重建、多相机严格同步、高速运动分析），可升级到 IEEE 1588 PTP 硬件时间同步。本节为可行性调研结论。

### 16.1 PLC 侧：Beckhoff EL6688

- [EL6688 官方页](https://www.beckhoff.com/en-en/products/i-o/ethercat-terminals/el6xxx-communication/el6688.html)：EtherCAT 端子形态的 IEEE 1588 时钟，支持 PTPv1/v2，经 EtherCAT DC 系统同步，使 TwinCAT 任务时间挂到 PTP 时间域；TwinCAT System Manager 中可选 `SlaveOnly` / `MasterOnly` / `Best Master Clock`。
- 物理规格：12 mm 端子、E-bus 供电、PTP 网口为 10/100 M。
- 价格参考（第三方渠道，波动大）：全新约 $900–2,600（[NEX $972](https://www.nexinstrument.com/el6688)、[PLC Direct $2,594](https://plc-direct.com/products/el6688)），二手/拆机约 $190–900（[eBay ~$189](https://www.ebay.com/itm/185596768016)）。
- **关键前提（最大不确定性）**：EL6688 必须插到**机器人控制器自己的 EtherCAT 总线**上并由其 TwinCAT 工程配置，**绕不开机器人工程师**。需确认：① 控制器是否有可扩展 E-bus 端子排；② 是否允许改 TwinCAT 工程；③ PLC 侧时间如何暴露给采集端。

### 16.2 相机侧：海康 GigE 工业相机 PTP

- 海康机器人 GigE 面阵相机**原生支持 IEEE 1588 PTP v2**：在 MVS 客户端 Transport Layer 参数中启用 IEEE 1588 V2，相机可设 Master/Slave，配合主机端 linuxptp（`ptp4l`）完成同步（[CSDN 实践](https://blog.csdn.net/lovely_yoshino/article/details/139663302)）。帧时间戳经 MVS SDK 的 `MV_FRAME_OUT_INFO_EX.nTimeStamp` 读出，PTP 使能后即在 PTP 时间域。
- GigE Vision 2.0 以 PTP 为多相机同步基础，配合 Action Commands 可做 µs 级软触发（[Basler 说明](https://www.baslerweb.com/en/learning/multi-camera-systems-gige-vision-2.0/)）。
- **USB 接口工业相机不支持 PTP**（[IDS 技术说明](https://cn.ids-imaging.com/techtipp-details/items/ptp_clock_comparison.html)）：现有 USB 腕部相机与采集卡内窥镜均不在 PTP 体系内。
- 价格参考（淘宝在售，含拆机件）：MV-CA050-10GM/GC（500 万像素 IMX250 全局快门，~100 fps 级）约 ¥480–1,300，官方全新约 ¥1,500–3,000；三台腕部相机预算约 ¥5,000–10,000。

### 16.3 PTP 化整体架构

```text
        Grandmaster（三选一）
   A. 某台相机设 Master（最简单，仅相机间同步）
   B. 采集 PC + Intel I210/I226 网卡（ptp4l，Windows 支持差）
   C. PLC 侧 EL6688 设 Master（以 PLC 为基准，与现状一致）
                  │ PTPv2
        ┌─────────┼─────────┐
   GigE相机1  GigE相机2  GigE相机3   （Slave，曝光时刻直接打 PTP 时间戳）
   机器人控制器 E-bus 上的 EL6688（Slave）→ TwinCAT 任务时间挂到 PTP 域
```

采集端改动：相机采集从 OpenCV/DirectShow 换成 MVS SDK / GenICam，直接读帧自带 PTP 时间戳；事后漂移校准可完全省掉。

### 16.4 风险与建议路径

| 风险 | 说明 |
|---|---|
| 机器人工程师配合度 | EL6688 涉及控制器硬件 + TwinCAT 工程，是关键路径 |
| Windows PTP 主机 | linuxptp 在 Linux 成熟；Windows 采集 PC 建议让相机/PLC 当 Master，或配 I210/I226 网卡 |
| 内窥镜无法 PTP 化 | 采集卡→USB 链路不在 PTP 体系；主视野若要曝光时刻需另选 GigE 方案 |
| 必要性 | 当前 ~1 ms 事后校准对 30 Hz 已够；PTP 收益在曝光时刻精度与零校准 |

**建议路径**：

1. 先与机器人工程师确认 EL6688 可行性（关键路径）；
2. 先单买一台海康 GigE 相机（约 ¥1,500）验证 MVS + PTP 采集链路（相机互为 Master/Slave，不依赖 PLC 侧）；
3. 两步验证通过后再决定是否上完整 PTP 体系。

### 17.2 `pack_session.py`：SurgSync 风格打包

**工具**：`scripts/tools/pack_session.py`

```bash
python scripts/tools/pack_session.py --session sessions/<session_name> [--verify]
```

**输出布局**（`packed/<session_name>/`）：

```text
├── video/<camera>.mkv                 # FFV1 level 3，全 I 帧，bit-exact
├── frames/<camera>.parquet            # 每帧时间戳；第 i 行 == 视频第 i 帧
├── robot_pose/robot_pose_arm<N>.parquet
├── session.json                       # 原样拷贝
├── episode_meta.json                  # episode 摘要（task 字段待标注填入）
└── manifest.json                      # 所有文件的 SHA-256
```

**对齐契约（关键设计）**：视频容器不承担时间同步职责。`frames/<camera>.parquet` 的第 i 行对应视频第 i 帧，行内带 PLC 时间轴时间戳；任意帧时刻的机器人关节状态通过对 `robot_pose/*.parquet` 做 LERP/SLERP 插值获得（即 `align_camera_anchor.py` 的做法）。帧↔关节的对齐精度与打包前完全一致。

**验证结果**（`--verify` 全量解码比对 SHA-256）：

| session | 内容 | PNG 原始 | FFV1 mkv | bit-exact |
|---|---|---|---|---|
| test_sync_start | 480p × 517 帧 | ~100 MB | 53.6 MB | ✅ PASS |
| test_cam1_720p_png30 | 720p × 601 帧 | 233 MB | 104.9 MB | ✅ PASS |

压缩率约 45–54%，且**数学无损**（任意帧可逐像素还原，满足训练清晰度要求）。

**实现要点**：conda ffmpeg 的 Windows 构建不支持 glob 输入、concat demuxer 对静态图片有时间戳丢弃问题，因此采用 **OpenCV 解码 PNG → rawvideo BGR24 管道喂给 ffmpeg** 的方式，帧数与像素由管道侧完全控制。ffmpeg 经 `conda install -c conda-forge ffmpeg` 安装，`pyarrow` 用于 parquet。
