## 1. 项目目标

构建一套稳定、可扩展的多模态手术数据采集平台，用于同步记录：

- **视觉数据**：内窥镜（高清）+ 双臂相机（手腕视角）
- **运动学数据**：通过 TwinCAT ADS 从 PLC 读取机器人末端执行器位姿

采集结果以结构化 session 形式落盘，供后续时间对齐、数据清洗与模型训练使用。

## 2. 硬件配置

| 设备 | 连接方式 | OpenCV 索引 | 用途 | 实测能力 | 备注 |
|---|---|---|---|---|---|
| 海康内窥镜 | 采集卡 → USB | `0` | 主视野 / arm_2 | 1280×720 @ 60 fps | 性能最好，建议作为 arm_2 |
| 双臂 USB 相机 A | USB | `1` | 左腕 / arm_1 | 640×480 @ ~22.5 fps | 物理上限约 22.5 fps |
| 双臂 USB 相机 B | USB | `3` | 右腕 / arm_3 | 640×480 @ ~22.5 fps | 物理上限约 22.5 fps |
| 额外 USB 相机 / 笔记本前置 | USB / 内置 | `2` | 可选 | 640×480 @ 30 fps | 可根据需要替换 arm_1 或 arm_3 |
| TwinCAT PLC | 网线 + ADS | — | 四臂机器人位姿 + 夹钳/能量状态 | 目标 1 kHz，实测 320–340 Hz（全 8 类符号） | AMS NetID `169.254.226.99.1.1`，端口 `851`；`output_all_arms=true` |

> **注意**：USB 相机在 Windows DirectShow 下的索引顺序可能因插拔、驱动加载顺序而变化。每次更换硬件布局后，应运行 `camera_assignment_setup.bat` 重新分配索引。

## 3. 软件架构

### 3.1 核心模块

```text
scripts/
├── acquisition/
│   ├── session.py              # Session 编排器：统一时钟、目录、writer
│   ├── base_source.py          # 数据源抽象基类
│   ├── timestamp.py            # 统一时间戳工具
│   ├── sources/
│   │   ├── twincat.py          # TwinCAT ADS 源
│   │   ├── usb_camera.py       # 线程内 USB 相机源（已弃用于 arm_2）
│   │   └── usb_camera_process.py   # 独立进程 USB 相机源
│   └── process_workers/
│       └── usb_camera_worker.py    # 子进程采集 worker
├── tools/
│   ├── camera_assignment_setup.py  # CLI 摄像头分配 + 真实 FPS benchmark + 参数选择
│   ├── camera_assignment_gui.py    # GUI 摄像头分配
│   ├── preview_single_camera.py    # 单摄像头实时预览
│   ├── preview_connected_cameras.py # 批量探测摄像头能力
│   ├── manual_acquisition.py       # 手动启停采集
│   └── start_manual_acquisition.bat # 一键启动批处理
└── config/
    ├── default.yaml                # 当前工作配置（setup/manual 默认修改/读取对象）
    ├── single_arm.yaml             # 单臂 fallback 配置
    └── three_cameras.yaml          # 三相机生产配置
```

### 3.2 设计要点

- **独立进程采集**：每个 USB 相机运行在独立 OS 进程（`process_camera`），避免 Windows DirectShow 多线程冲突，且单个相机的写盘瓶颈不会影响其他源。
- **统一 Session 管理**：`AcquisitionSession` 负责创建 session 目录、注册所有源、启动/停止采集、写入 `session.json`。
- **Writer 线程**：
  - 进程相机自包含 writer（子进程内）。
  - TwinCAT 数据由 Session 的主 writer 线程写入 CSV。
- **信号处理**：支持 `Ctrl-C` / `Ctrl-Break` 优雅停止。

## 4. 数据源与格式

### 4.1 视觉数据

| 字段 | 说明 |
|---|---|
| 存储格式 | JPG（推荐；如后续有标定/无损需求可单独切换为 PNG） |
| 命名规则 | `{source_name}_{frame_idx:08d}_{timestamp_ns}.{format}` |
| 元数据 | `metadata.csv`：index, timestamp_ns, pc_arrival_ns, timestamp_beijing, filename, width, height |
| 时间戳 | `timestamp_ns` 基于 `host_realtime`（`time.time_ns()`），单调递增 |

### 4.2 TwinCAT 机器人位姿

| 字段 | 说明 |
|---|---|
| 文件 | `robot_pose/robot_pose_arm<N>/twincat_poses.csv`（每条臂独立一个 CSV，`N=1..4`） |
| 主时间戳 | `timestamp_ns` = PLC CycleCount × CycleTime（PLC 时间轴） |
| PC 时间戳 | `timestamp_ns_pc` = 主机收到 ADS 响应时的 PC 时间 |
| RTT | `rtt_ns` = ADS 请求往返延迟 |
| 数据列 | `position_x/y/z`、`orientation_w/x/y/z`、`scope_position_x/y/z`、`joint_1`~`joint_12`、`instrument_type`、`gripper_angle`、`gripper_signal`、`energy_instrument_status` |
| 多臂模式 | `output_all_arms: true` 时，一次 ADS 读取生成 4 个样本，分别落入 `robot_pose_arm1` ~ `robot_pose_arm4` |

### 4.3 session.json

每个 session 根目录下的元数据文件，记录：

- session 名称、起止时间、持续时间
- `clock_source`、`clock_offset_ns`
- 各源样本数、配置摘要

## 6. 时间戳策略

### 6.1 当前策略：`clock_source = host_realtime`

- 视频帧的 `timestamp_ns` 使用 PC  wall time。
- TwinCAT 样本的主 `timestamp_ns` 使用 PLC CycleCount 时间（PLC 时间轴）。
- TwinCAT metadata 同时记录 PC 到达时间 `timestamp_ns_pc`。

### 6.2 为什么不用 `twincat_master`

早期尝试过 `clock_source = twincat_master`，由 TwinCAT 源动态更新 `offset_ns`，使视频时间戳对齐 PLC 时间轴。但发现：

- TwinCAT offset 随采集过程收敛/漂移。
- 不同相机子进程在启动时抓取的 offset 不同，导致跨相机时间戳不一致。
- 视频时间戳出现非单调甚至递减。

因此改为 `host_realtime` + 事后漂移校准方案（见第 9 节）。

### 6.3 事后对齐接口

TwinCAT CSV 已包含：

- `timestamp_ns`（PLC 时间）
- `timestamp_ns_pc`（PC 时间）
- `pc_arrival_ns`
- `twincat_cycle_count`
- `rtt_ns`

可据此建立 `PLC_time = f(PC_time)` 的线性映射，再校准视频 `timestamp_ns`。

## 7. 操作工具

### 7.1 摄像头分配：`camera_assignment_setup.bat` / `camera_assignment_setup.py`

- 双击运行（GUI 批处理）或在命令行运行 CLI 版本。
- 探测 0-9 索引摄像头，对每个分辨率 + 格式组合做**真实 FPS benchmark**。
- 显示每个摄像头的预览图和实测帧率。
- 用户选择每个摄像头对应哪条臂（arm_1/arm_2/arm_3）。
- 为每条臂选择：分辨率、目标 FPS（不超过实测最大值）、FOURCC、保存格式。
- 自动更新 `scripts/config/default.yaml`（可用 `--config` 指定其他文件）。
- 未分配的臂会被标记 `enabled: false`。

### 7.2 单摄像头预览：`preview_single_camera.bat`

- 双击运行。
- 列出可用摄像头，用户输入索引。
- 实时预览，叠加分辨率、FPS、按键提示。
- 支持连续预览多个摄像头：关闭一个后询问是否继续。
- 快捷键：`q/ESC/X` 退出，`s` 保存快照。

### 7.3 手动采集：`start_manual_acquisition.bat`

- 双击运行。
- 自动生成 `test_YYYYMMDD_HHMMSS` 格式 session 名（北京时间）。
- 按 Enter 开始，按 Enter 停止。
- 实时打印各源样本数。

## 8. 当前主配置

`scripts/config/default.yaml`（由 `camera_assignment_setup` 生成和维护）：

| 源 | 类型 | 索引 | 分辨率 | FPS | 编码 | 格式 |
|---|---|---|---|---|---|---|
| robot_pose | twincat | — | — | 1 kHz 目标，实测 ~320–340 Hz | — | CSV（per-arm） |
| camera_arm_2 | process_camera | 0 | 1280×720 | 60 | MJPG | JPG |
| camera_arm_1 | process_camera | 1 | 640×480 | 22 | MJPG | JPG |
| camera_arm_3 | process_camera | 3 | 640×480 | 22 | MJPG | JPG |

TwinCAT 配置要点：

- `output_all_arms: true`：同时输出 arm_1 ~ arm_4。
- `timestamp_mode: twincat`：主时间戳使用 PLC CycleCount。
- `output_dual_timestamps: true`：同时记录 PC 时间戳，便于事后漂移校准。
- 默认读取 PLC 全部 8 类符号：关节角、末端位置（臂/镜体坐标系）、姿态四元数、器械类型、夹钳角度、夹钳信号、能量器械状态。

> `camera_arm_1` / `camera_arm_3` 的物理上限约为 22.5 fps，配置值按实测能力填写。若需要更高帧率，可尝试将 camera 2（实测 30 fps）分配给 arm_1 或 arm_3。

## 9. 已知问题与限制

### 9.1 已解决

| 问题 | 解决方案 |
|---|---|
| 内窥镜 1280×720 PNG 写盘跟不上 30 fps | 改为 JPG；独立进程避免拖累其他源 |
| 相机时间戳不单调/不一致 | `clock_source` 改为 `host_realtime` |
| 子进程输出路径错误 | `session_dir` 使用绝对路径 |
| 批处理闪退 / 中文乱码 | 转换为 GBK + CRLF；交互脚本只重定向 stderr |
| 点击 OpenCV 窗口 X 按钮无法退出 | 检测 `WND_PROP_VISIBLE` |
| arm_1 / arm_3 帧率不足原因不明 | 单摄像头 benchmark 确认物理上限约 22.5 fps，与编码/并发无关 |
| 摄像头分配工具不能选择录制参数 | 增强 `camera_assignment_setup.py`，支持分辨率/FPS/格式/FPS benchmark |
| 配置文件管理混乱 | 新增 `default.yaml` 作为工作配置；`single_arm.yaml` 作为单臂 fallback；`three_cameras.yaml` 作为三相机生产配置 |
| TwinCAT 仅采集单臂 | `output_all_arms: true` 实现四臂同时采集；同一次 ADS 读取生成 4 条臂同 cycle 数据 |
| TwinCAT 未采集夹钳/能量状态 | 默认符号扩展到 PLC 暴露的全部 8 类数组 |

### 9.2 待解决 / 需讨论

| 问题 | 影响 | 建议方案 |
|---|---|---|
| `camera_arm_1` / `camera_arm_3` 物理上限约 22.5 fps | 双臂数据密度低于 30 fps 目标 | 接受 22.5 fps；或替换为 camera 2（30 fps）等更高性能相机 |
| `robot_pose` 实际 320–340 Hz（全 8 类符号），未达 1 kHz | 运动学时间分辨率受限 | 优化 TwinCAT PLC 任务周期/ADS 路由；或减少读取符号数量；或接受当前 Python 端上限 |
| 长时间采集稳定性 | 仅验证到 5 分钟 | 做 10-30 分钟连续测试，观察队列、丢帧、磁盘 I/O、ADS 连接 |
| TwinCAT PLC 与 PC 时钟漂移 | 跨模态时间对齐误差 | 验证 `calibrate_temporal_drift.py` 的事后校准流程 |

### 9.3 已预留并部分验证

- RTT 延迟校正（TwinCAT `use_rtt_correction`）：✅ 已验证可用。
- 多 ADS 连接（`num_connections=2`）：✅ 已验证，采样率从 320 Hz 提升到 650 Hz，但伴随重复 CycleCount。
- 事后漂移校准脚本 `scripts/tools/calibrate_temporal_drift.py`：已预留，待实际采集数据验证。

## 10. 下一步工作建议

1. **确认最终摄像头分配**：运行 `camera_assignment_setup.bat` / `.py`，根据实测 FPS 为三条臂选择最优相机和参数。
2. **长时间稳定性测试**：连续采集 10-30 分钟，检查丢帧、磁盘写入、内存占用、ADS 连接；重点关注全 8 类符号 + 四臂输出时的稳定性。
3. **实现/验证事后时间校准**：用 TwinCAT 双时间戳建立 PLC-PC 映射，校准视频时间戳。
4. **robot_pose 速率优化**：若 1 kHz 是硬性需求，需检查 TwinCAT PLC 任务周期/ADS 路由，或减少读取符号数量；否则明确接受当前 320–340 Hz。
5. **数据对齐准备**：采集一组包含明显运动的标定数据，验证 `calibrate_temporal_drift.py` 的校准效果。
